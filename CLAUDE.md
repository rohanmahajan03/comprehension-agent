# CLAUDE.md

Adaptive concept tutor: ingests textbook chapters, builds a concept dependency graph, and runs a Q&A loop that traces wrong answers back to the prerequisite concept at fault. `graph_builder.py` (pipeline 1, step 2), `question_generator.py` (pipeline 1, step 3), `evaluator.py` (pipeline 2, step 2), and `diagnoser.py` (pipeline 2, steps 3-5) all make real LLM calls.

## Commands

```bash
# Full stack, dev mode (hot reload both services via bind mounts)
cp .env.example .env          # once
docker compose up             # frontend :5173, backend :8000

# Production-like (nginx serving built frontend, no mounts)
docker compose -f docker-compose.yml up --build

# Backend natively
cd backend && python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"       # uv works too: uv sync --extra dev
uvicorn app.main:app --reload

# Backend tests (free — all four services are stubbed via tests/conftest.py, live geval suites auto-skip)
cd backend && .venv/bin/pytest

# G-Eval regression suite for evaluator.py (real, billed Anthropic API calls — see Testing below)
cd backend && set -a && source ../.env && set +a && .venv/bin/pytest tests/geval -v

# Structural regression suite for graph_builder.py (real, billed Anthropic API calls — see Testing below)
cd backend && set -a && source ../.env && set +a && .venv/bin/pytest tests/graph_geval -v

# Regression suite for question_generator.py (real, billed Anthropic API calls — see Testing below)
cd backend && set -a && source ../.env && set +a && .venv/bin/pytest tests/question_geval -v

# Frontend natively
cd frontend && npm install && npm run dev   # proxies /api to :8000
npm run build                                # tsc -b && vite build
```

## Architecture

Two pipelines in `backend/app/services/`:

1. **Pre-questioning** (per uploaded chapter): `POST /api/textbook` → `graph_builder.build_graph()` (real LLM call) → `question_generator.generate_questions()` (real LLM call, one per concept), all synchronous, results saved to the store.
2. **Diagnostic loop** (per study session): `POST /api/study-session/{id}/answer` → `evaluator.evaluate()`. Correct → advance `current_concept_id` in topological order. Incorrect → `diagnoser.diagnose()` returns a targeted question probing a prerequisite; study session status becomes `diagnosing`. Both `evaluator.evaluate()` and `diagnoser.diagnose()` are real.

`evaluator.py` calls `claude-haiku-4-5` via the Anthropic SDK with a JSON-schema-constrained response (`_OUTPUT_SCHEMA`) grading the student's answer against `question.expected_answer_notes`. It's the template `graph_builder.py` and `question_generator.py` followed (`diagnoser.py` needed a different shape — see below). Known issue: the `temperature=0` call parameter is currently commented out, which means grading is **not deterministic** — the same question/answer pair can flip between `correct: true/false` across calls. Re-enabling it is recommended; the `tests/geval` suite (see Testing below) is what surfaced this.

`graph_builder.py` calls `claude-haiku-4-5` (with `temperature=0`, unlike `evaluator.py`) with a JSON-schema-constrained response asking for `{concepts: [{id, label, summary}], edges: [{from, to, evidence}]}` extracted from the chapter text. `_extract_raw_graph()` does the LLM call + parsing + dedup and returns that raw shape (still carrying each edge's `evidence` quote, un-namespaced ids) — it's an internal seam, not stable public API, kept separate so `tests/graph_geval` can grade edge evidence directly. `build_graph()` folds `edges` into each `Concept.depends_on` (`to` depends on `from`) *and* `Concept.evidence` (`{prereq_id: quote}`, one entry per `depends_on` id — the source-text justification for that specific prerequisite, not persisted anywhere before this). It also skips any edge that would introduce a cycle when building `depends_on`/`evidence`, since `topological_order` (`graphlib.TopologicalSorter`) assumes a DAG and would otherwise raise unhandled.

`question_generator.py` calls `claude-sonnet-4-6` (with `temperature=0`) once per concept, with a JSON-schema-constrained response asking for a `{concept_id, questions: [{type, question, expected_answer, grounding}]}` set drawn only from that concept's own evidence anchor (its `summary`), its prerequisites (each with the specific `evidence` quote justifying that dependency, from `Concept.evidence`), and its siblings (other concepts sharing at least one direct prerequisite — concepts with no prerequisites of their own have no siblings). `generate_questions(graph)` mutates every `Concept.questions` in the passed-in graph **in place** (returns `None`) rather than returning a separate map, so the graph stays the single source of truth for a concept's question set; the ingestion router still mirrors each concept's `questions` into the store's separate question index afterward, since `study_session.py` and `routers/questions.py` look questions up there (and diagnostic questions get appended there too). Each question also carries an `expected_answer` — the ideal student response, in prose — and `question_generator.format_answer_notes()` passes it through **verbatim** as `Question.expected_answer_notes` (nothing wrapped around it, `grounding` not appended). That field is what `evaluator.py` labels `RUBRIC:` and grades against, and the bare-prose shape is deliberate: it is exactly what `tests/geval` has always fed the evaluator (its hand-written `golden_answer` fixtures), so production and the suite validating it stay the same kind of input. Prompt rules 8 and 9 govern it — state the substance in full and never defer to context the evaluator cannot see ("as the passage says"), since it receives only the question, this text, and the student's answer; and match the question type (name every required item for `enumeration_completeness`; for `open_ended_example`/`applied_reasoning`, where the correct answer is the student's own and won't appear in the evidence, write what any valid answer must demonstrate rather than one specific example). **This field was a bug fix.** Before it existed, `expected_answer_notes` was the `grounding` quote prefixed "A correct answer is grounded in: ..." — a source passage, which says where a question came from, not what an answer needs. The evaluator was left inventing the decomposition per call (compounding the `temperature=0` non-determinism below), and it was actively wrong for the open-ended types. `tests/geval` never caught it because its fixtures always supplied a proper model answer: the suite was measuring the evaluator under rubric conditions production never produced, which is why its 39/42 was a ceiling rather than a description of real grading. Rule 7 of the system prompt ("treat each [evidence] passage as atomic... quote every passage in full, never truncate mid-clause") was added after `tests/question_geval` caught the model truncating a second evidence source mid-sentence on `conceptual_distinction` questions that combine two sources. It was strengthened once more after that first version still let one case through — the model would compress/drop a passage it judged redundant with another passage it was also quoting; rule 7 now explicitly says redundancy between passages is never a reason to shorten either one (see Testing below).

`diagnoser.py` is the one service that is **not** a single structured call — it runs a bounded agentic tool-calling loop over `claude-sonnet-4-6` (design doc: `docs/specs/2026-08-10-diagnoser-agentic-pipeline-design.md`). `diagnose(concept, graph, question, answer, evaluation)` takes the evaluator's `EvaluationResult` as its starting signal (what the answer failed to show) and gets `_MAX_TURNS = 5` round-trips: 4 investigative, then a forced final one where `tool_choice` is pinned to `submit_diagnosis` with only that tool declared, so the loop always ends in a real model judgment rather than a code-side default. Four tools, all executed locally: `get_prereqs` (pure graph lookup — the model calls it on a prerequisite's own id to walk deeper, which is how multi-level drilling happens in one call), `pull_question_from_storage` (reads `Concept.questions`, then `_find_matching_question()` asks `claude-haiku-4-5` whether any candidate actually targets *this* deficiency — a semantic judgment, not keyword overlap), `generate_question` (nested `claude-sonnet-4-6` call), and `submit_diagnosis`. **The certainty gate is code-enforced, not just prompted**: `_accept_diagnosis()` rejects any submission below `"high"` confidence by returning an `is_error` tool_result, so the model cannot end the loop by asserting confidence — and each rejection states its actual reason (bad concept id / bad question id / missing question text), since a generic message would send the model chasing the wrong fix. Parallel tool use is disabled so one tool call = one turn and the budget accounting stays exact. `confidence`/`evidence_basis` are folded into `DiagnosisResult.reasoning` as prose rather than becoming new schema fields.

Key seams:

- **Storage**: `backend/app/store/memory_store.py` — abstract `Store` class + `InMemoryStore` + `get_store()` factory (lru_cache singleton). Swapping in Postgres = new subclass + change `get_store()`.
- **Models**: `backend/app/models/schemas.py` is the source of truth; `frontend/src/types/index.ts` mirrors it **by hand — keep them in sync** (includes `AnswerResponse`, the answer-endpoint envelope). The study-session domain model is named `StudySession`/`StudySessionStatus` (not `Session`) specifically so it won't collide with a future DB session object (e.g. SQLAlchemy's `Session`) once Postgres is wired in. `Question` is defined before `Concept` in `schemas.py` specifically so `Concept.questions: list[Question]` can reference it directly without a forward ref.
- **ID conventions (load-bearing)**: concept ids are `{doc_id}:{slug}`, question ids are `{concept_id}:{suffix}` (`q1`, `q2`, `diagnostic1`, `diagnostic2`, …). The study-session router (`routers/study_session.py`) resolves an answered question by `question_id.rsplit(":", 1)[0]` → concept's question set. Diagnostic suffixes are **numbered** (`diagnoser._next_diagnostic_id()`) because one concept can be diagnosed more than once in a session with a different gap each time; a fixed `:diagnostic` suffix would collide, and since the router dedupes by id it would silently keep serving the first question's rubric against the second question's prompt. When a diagnostic question is generated, `submit_answer` appends it **both** to the store's question index (so answers to it resolve) **and** to the suspect's `Concept.questions` on the graph, followed by `store.save_graph(graph)` — the graph copy is what `pull_question_from_storage` reads, so without it a question generated in one diagnostic round would be invisible to a later round on that same concept.
- Concept ordering uses `graphlib.TopologicalSorter` (`graph_builder.topological_order`).

## Stub behavior (intentional, don't "fix")

All four services make real LLM calls now (see Architecture above), so this section is empty. `tests/conftest.py` stubs every one of them (`stub_evaluator` alternates correct/incorrect via a global counter; `stub_graph_builder` returns the old fixed 5-concept calculus graph; `stub_question_generator` sets two templated questions per concept in place; `stub_diagnoser` reproduces the old "pick the first `depends_on` entry" behavior) so `test_flow.py` and friends stay free and deterministic.

## Testing

- **Stub-backed tests** (`backend/tests/test_flow.py`, `test_health.py`): free, fast, no API key needed. `tests/conftest.py` monkeypatches `evaluator.evaluate`, `graph_builder.build_graph`, `question_generator.generate_questions`, and `diagnoser.diagnose` with deterministic stubs (autouse fixtures) so these never hit the real API.
- **`backend/tests/geval/`** — a G-Eval regression suite (via [DeepEval](https://github.com/confident-ai/deepeval)) that runs the *real* `evaluator.evaluate()` against the 10 questions/42 answer variants in `tests/geval_test_suite.md`, then scores the evaluator's explanation against the golden answer using a `GEval` metric judged by a separate model (`claude-opus-4-5`, deliberately different/stronger than the `claude-haiku-4-5` evaluator under test, to avoid a model grading its own homework).
  - Organized one file per chapter (`test_ch1.py`…`test_ch8.py`), one test function per question/answer-variant pair.
  - `criteria.py` holds each question's G-Eval `criteria` (copied from the markdown) and `evaluation_steps`, hand-derived and **hardcoded** — GEval would otherwise regenerate steps via an LLM call on every run, making the rubric non-deterministic across runs. If a question's criterion changes, regenerate its steps by hand and update `criteria.py`; don't let evaluation_steps go unset.
  - `tests/geval/conftest.py` overrides the parent `stub_evaluator` fixture as a no-op (real calls needed) and skips the whole directory if `LLM_API_KEY` is unset, so CI (which has no key) stays green.
  - **Makes real, billed Anthropic API calls** — roughly $0.35–0.45 and 5-6 minutes for a full run (Opus judge calls dominate cost). Don't run this suite reflexively; it's for validating changes to `evaluator.py`'s prompt/model.
  - As of the last full run: 39/42 passing. The 3 known failures are real evaluator leniency gaps (not suite bugs) — see git history around the `evaluator implementation done` / `g-eval test suite` commits for details.
- **`backend/tests/graph_geval/`** — a structural regression suite for `graph_builder.py`, built from the 4 DDIA excerpts in `tests/graph_golden_set.md` (hand-curated expected concepts/edges/"forbidden" ideas per case). Different shape than `tests/geval/` since the output under test is a graph, not free text:
  - Runs the real `graph_builder._extract_raw_graph()` on each case's source text, then aligns the extracted concepts to the golden concepts by meaning via a judge LLM call (`claude-sonnet-4-5` — cheaper than Opus since this is structural matching, not open-ended judgment; still stronger than the `claude-haiku-4-5` extractor under test). Edge quoted-evidence is checked deterministically (no LLM call): every edge's `evidence` must be a verbatim (whitespace-normalized) substring of the source text.
  - `golden.py` hardcodes each case's expected concepts/edges/forbidden-ideas; source text itself is *not* duplicated there — it's parsed straight out of `graph_golden_set.md`'s fenced code blocks so it can never drift from what the evidence check validates against.
  - One file per case (`test_case1.py`…`test_case4.py`), 4 tests each: concept recall ≥ 0.8, zero forbidden-idea leaks, edge recall ≥ 0.6, all edge evidence verbatim. `support.score_case()` is `lru_cache`d per case so those 4 assertions share one extraction call + one alignment call rather than re-running the real API per assertion.
  - `tests/graph_geval/conftest.py` overrides the parent `stub_graph_builder` fixture as a no-op and skips the whole directory if `LLM_API_KEY` is unset, same pattern as `tests/geval/`.
  - As of the first full run: 8/16 passing. Spot-checked each failure against the raw model output — none are harness bugs, all are genuine gaps in current `graph_builder.py` output: (1) edge recall is the weakest area — the model frequently extracts the right concepts but under-connects them (e.g. Case 4's `oltp → olap → data_warehouse` backbone edges are missing even though all three concepts matched); (2) some individually quiz-worthy sub-concepts (Case 2's `dirty_read`/`dirty_write`/`read_skew`/`race_condition`) are getting folded away — likely a side effect of the "be strict about what counts as a concept" prompt tightening earlier in this suite's development; (3) two forbidden-idea leaks (Case 2's "Weak Isolation Levels" and Case 3's generic "Index" each got their own node despite the source text treating them as folded-in/anti-pattern); (4) two edges with paraphrased-not-verbatim evidence quotes. Not yet triaged into "prompt needs tuning" vs. "golden expectations too strict" — see conversation/PR history for the analysis.
- **`backend/tests/question_geval/`** — a regression suite for `question_generator.py`, covering Case 3 — Storage Engines (all 11 concepts) from `tests/graph_golden_set.md`. Unlike `tests/graph_geval/`, no judge LLM call is needed for alignment: the input graph is constructed directly (concept ids/labels/edges reused from `tests/graph_geval/golden.py` so the two suites can't drift on graph shape; a runtime assertion in `build_graph()` guards against drift), so the generator's output is already keyed to known concept ids and the `type` field is a closed vocabulary — no fuzzy matching required.
  - Runs the real `question_generator._generate_raw_for_concept()` per concept (the same "internal seam, not stable public API" pattern as `graph_builder._extract_raw_graph()` — exposes each raw `{type, question, expected_answer, grounding}` before `generate_questions()` folds it into a `Question`, discarding `type` and passing `expected_answer` through as `expected_answer_notes`). Scores five ways — two on the question, two on the model answer, one on the grounding quote behind both: (1) type recall — for each golden `(concept, type)` pair, did the generator produce at least one question of that type; (2) grounding fidelity, checked two ways against the exact evidence-anchor texts sent to the LLM for that concept (`concept.summary` + each prerequisite's own `summary` **and** specific `evidence` quote, per `_describe()` — not just the quote — + each sibling's `summary`): (a) truncation — for each individual source text, if `grounding` shares a long prefix with it but doesn't contain it in full, that source was cut off mid-clause; checked per-source-text (`support._truncated_sources()`) rather than by splitting `grounding` on punctuation, because the model joins multiple quoted sources with delimiters (`, `, `; `, ` | `, …) that vary run to run and can collide with punctuation already inside a source text — an earlier sentence-split-based version of this check produced false positives for exactly that reason; (b) coverage — a coarse fabrication check, the fraction of `grounding`'s tokens found anywhere in the source texts (`support._token_coverage()`), since the truncation check alone only fires when a source is *partially* quoted, not when it's invented from nothing; (3) semantic similarity — an LLM-judged score (`support.judge_similarity()`, `claude-haiku-4-5`, `_SIMILARITY_SYSTEM_PROMPT`) for each matched pair, on a 0.0-1.0 scale with explicit rubric bands ("same ask reworded" / "same core, minor scope diff" / "same concept, different facet" / "different concept, drifted"), asserted as an aggregate average across all matched pairs rather than per-pair (a single legitimately-different-facet question can still drag one pair's score down without the generator being wrong).
    - Originally a bag-of-words cosine metric (no embedding API/key, kept the suite free). Replaced after a manual spot-check (across two live runs, full similarity range ~0.16–0.71) found it mostly flagged genuine paraphrases as false positives, with too little precision to trust as a real signal — e.g. one low-scoring pair turned out to test a different-but-still-valid facet of the same evidence, not a generator defect. An LLM judge distinguishes "reworded" from "actually different" far better than word overlap; first live run with the new judge (`average_similarity` ≈ 0.687) confirmed this — e.g. it correctly separated near-paraphrases (0.85–0.95) from a `sstable` `conceptual_distinction` pair scored 0.15, correctly identifying that the generated question tests a different contrast (SSTable-vs-log-segment structure) than the golden question asks about (which prior process enforces key uniqueness) despite sharing a type label and concept.
    - Note on judge choice: `tests/geval` and `tests/graph_geval` deliberately use a judge *stronger* than the model under test, to avoid "grading its own homework" — here the model under test is `claude-sonnet-4-6`, so Haiku judging its output is the *reverse* of that pattern (a deliberate choice; revisit if Haiku's judgments prove unreliable). Justified as: this judgment ("do two questions test the same understanding") is a narrower, more mechanical comparison than open-ended quality grading — closer to graph_geval's structural alignment call (also a cheaper-than-everything-else judge) than to geval's rubric grading.
    - `LOW_SIMILARITY_FLAG = 0.6` (informational only, not a pass/fail condition) matches the judge's own rubric boundary between "same core understanding" and "different facet or worse." `AVERAGE_SIMILARITY_THRESHOLD = 0.6` calibrated against the same live run (comfortably below the observed 0.687).
  - `golden.py` hand-curates one or two genuinely-appropriate-type reference questions per concept (not all 5 types forced) plus each concept's `summary`/prerequisite-`evidence` text, written as close paraphrases of the Case 3 source text (not required to be verbatim, same as graph_builder's own summaries).
  - `tests/question_geval/conftest.py` overrides the parent `stub_question_generator` fixture as a no-op and skips the whole directory if `LLM_API_KEY` is unset, same pattern as the other two suites.
  - **Checks 4 and 5 grade the answer side**, added after the `expected_answer` bug fix (see Architecture). Until they existed the suite only tested the question-writing half of `question_generator`'s output, while the model-answer half — the entire rubric `evaluator.py` grades against — went untested. (4) *Expected-answer gradeability* (`CaseResult.expected_answer_violations`), fully deterministic, no LLM call: catches shapes the evaluator structurally cannot grade regardless of content — under `MIN_EXPECTED_ANSWER_CHARS = 40`, deferring to context it never receives (`_ANSWER_POINTER_RE`, e.g. "as the passage states"), or a verbatim copy of the `grounding` quote, which is precisely the old bug. Exact-match only on that last one, since a close paraphrase of the evidence is legitimate (for `conceptual_correctness` the ideal answer largely *is* the evidence restated). (5) *Answer quality* (`support.judge_answer_quality()`, `claude-haiku-4-5`), asserted as an aggregate rate ≥ `ANSWER_QUALITY_THRESHOLD = 0.9`: does the `expected_answer` actually and completely answer its own question, consistent with the evidence, standing on its own for a grader that never sees that evidence? The judge prompt carries two explicit allowances so it doesn't penalize correct behavior — describing what any valid answer must demonstrate (right for the open-ended types) and closely restating the evidence (right for `conceptual_correctness`). **Neither has been exercised against the live API yet** — both were added in the same change as the field, so the 3/3 figure below predates them.
  - As of the last full run: **3/3 passing** (type recall ≥ 0.6 ✓, 0.95 observed; average similarity ≥ 0.6 ✓, 0.687 observed; grounding fidelity ✓). Grounding-fidelity history, three fixes deep: (1) the first run found `question_generator.py` truncating a second evidence source mid-clause on `conceptual_distinction` questions (which combine two sources) — fixed by adding rule 7 to `_SYSTEM_PROMPT` ("treat each passage as atomic... quote every passage in full, never truncate mid-clause"); (2) re-running surfaced that the original sentence-split-based grounding check was itself flaky against the model's new (delimiter-varying) multi-quote joining style — replaced with the truncation+coverage check described above; (3) `write_amplification` still reproducibly failed after both of those, with a *different* specific manifestation each run despite `temperature=0` (dropping a middle clause; dropping a trailing sentence; substituting an em-dash with a stray artifact) — all centered on the same sentence, whose content overlaps between the target's own summary and the `lsm_tree` prerequisite's evidence. Root cause: the model was compressing/dropping a passage it judged redundant with another passage it was also quoting. Fixed by strengthening rule 7 to explicitly define a "passage" as the whole source text (not a sentence within it) and state that redundancy between passages is never a reason to shorten either one. Confirmed stable across two consecutive live runs after the fix (previously the failure recurred every run).

## Docker gotchas

- `docker-compose.override.yml` (auto-merged) is dev mode: vite dev server (Dockerfile `dev` target), `uvicorn --reload`, bind mounts. It uses `ports: !override` to replace (not append to) the base port mapping, and a **distinct image tag** (`comprehension-agent-frontend-dev`) so dev/prod builds don't clobber each other — if the frontend serves nothing on :5173, a stale image from the other mode is the likely cause; rebuild with `--build`.
- Prod frontend: nginx serves `dist/` and proxies `/api` → `backend:8000` (`frontend/nginx.conf`). Dev: vite proxies `/api` using `BACKEND_URL` env var (`vite.config.ts`).
- Backend `env_file: .env` means compose fails without `.env` — copy from `.env.example`.

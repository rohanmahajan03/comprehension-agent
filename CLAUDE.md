# CLAUDE.md

Adaptive concept tutor: ingests textbook chapters, builds a concept dependency graph, and runs a Q&A loop that traces wrong answers back to the prerequisite concept at fault. `graph_builder.py` (pipeline 1, step 2), `question_generator.py` (pipeline 1, step 3), `evaluator.py` (pipeline 2, step 2), and `diagnoser.py` (pipeline 2, steps 3-5) all make real LLM calls, as does `evidence_finder.py` (pipeline 1, graph review only). All five have live regression suites.

## Architecture

Two pipelines in `backend/app/services/`:

1. **Pre-questioning** (per uploaded chapter): `POST /api/textbook` → `graph_builder.build_graph()` (real LLM call) → `question_generator.generate_questions()` (real LLM call, one per concept), all synchronous, results saved to the store. **Unless the upload sets `review`** — see the review-mode bullet under Key seams, which splits this into extract-now/generate-after-approval.
2. **Diagnostic loop** (per study session): `POST /api/study-session/{id}/answer` → `evaluator.evaluate()`. The transition branches on the session's status **as read at request entry**, before anything mutates it (`docs/specs/2026-09-17-study-loop-remediation-design.md` §2, implemented): `ACTIVE`+correct advances `current_concept_id` in topological order; `ACTIVE`+wrong diagnoses and becomes `diagnosing`; **`DIAGNOSING`+correct splits on *which concept the probe was about*.** A probe aimed at another concept returns to `ACTIVE` with `current_concept_id` unchanged — the concept that failed is re-served, which is the return step the loop originally lacked (a correct diagnostic answer used to advance past it, marking it complete without it ever being demonstrated). A probe aimed at the answered concept itself **advances instead**: self-diagnosis is a real outcome (the diagnoser naming the concept it was asked about — the *only* possible outcome for a concept with no prerequisites, and what `stub_diagnoser` falls back to), so the probe *is* the demonstration and there is nothing to hand back. Reading "was a diagnostic" as "do not advance" made that case a treadmill — the loop returned to the same concept, `_pending_question` re-served the very question that started the drill, and a correct answer moved nothing, bounded only by `_MAX_CONCEPT_ATTEMPTS`. So the discriminator is the entry status **plus** a `question.concept_id != current_concept_id` comparison, not the question's provenance; `_diagnostic_question_ids()` is no longer consulted on this path at all. **Why no test caught it:** every test covering the return step started the session on the chapter's root concept, which by definition has no prerequisites, so all of them ran the self-diagnosis path while asserting prerequisite behavior — hence `test_flow.py`'s `_advance_to_a_dependent_concept()`, and a test per branch. See the 2026-09-21 amendment in `docs/specs/2026-09-17-study-loop-remediation-design.md` §2. `DIAGNOSING`+wrong diagnoses deeper. Two module constants bound the drill, `_MAX_CONCEPT_ATTEMPTS = 3` and `_MAX_DIAGNOSTIC_CHAIN = 2`, both derived from history on the read path so neither needed a migration (`_failed_main_track_attempts` counts by `HistoryEntry.effective_correct`, so a grade the student overrode is not a failed attempt — see the answer-override bullet); when either trips, the response's `revealed_answer` carries the abandoned question's `expected_answer_notes` and the loop moves on. `_advance()` skips concepts with an empty question set rather than parking on one (`question_generator` legitimately returns none for a concept, and parking there deadlocks the session); `start_study_session` applies the same guard, creating the session `COMPLETED` if no concept in the chapter has a question. Both `evaluator.evaluate()` and `diagnoser.diagnose()` are real.

`evaluator.py` calls `claude-haiku-4-5` via the Anthropic SDK with a JSON-schema-constrained response (`_OUTPUT_SCHEMA`) grading the student's answer against `question.expected_answer_notes`. It's the template `graph_builder.py` and `question_generator.py` followed (`diagnoser.py` needed a different shape — see below). It runs at `temperature=0`: it was commented out for a while, and the same question/answer pair flipped between `correct: true/false` across calls (`tests/eval_geval` surfaced this). **It grades against `Question.required_points`, not the model answer.** Students found grading too strict because `expected_answer_notes` is a complete model answer, and the evaluator treated every sentence of it as a requirement. Telling it the rubric was "more than a passing answer needs" overshot: with no floor it waved vague answers through as "elaboration", on Haiku and worse on Sonnet (36/42), because the evaluator was deciding what was essential on every call. So `question_generator` now decides that once per question (prompt rule 10, persisted as JSONB `questions.required_points`), and the evaluator's prompt labels the model answer `MODEL ANSWER:` and uses it only to interpret the `REQUIRED POINTS:`. A `point_checks` array in the output schema, before `correct`, makes it check each point before committing to a verdict; it is not surfaced, and `EvaluationResult` is unchanged. A point only counts if it is explained rather than named or restated. Questions with no points (written before the field existed, and every diagnostic probe, since `diagnoser.py` does not produce them) fall back to the evaluator identifying the points itself. The prompt also forbids crediting the student with an idea they did not express, because the explanation is the feedback the student reads.

`graph_builder.py` calls `claude-haiku-4-5` (with `temperature=0`, unlike `evaluator.py`) with a JSON-schema-constrained response asking for `{concepts: [{id, label, summary}], edges: [{from, to, evidence}]}` extracted from the chapter text. `_extract_raw_graph()` does the LLM call + parsing + dedup and returns that raw shape (still carrying each edge's `evidence` quote, un-namespaced ids) — it's an internal seam, not stable public API, kept separate so `tests/graph_geval` can grade edge evidence directly. `build_graph()` folds `edges` into each `Concept.depends_on` (`to` depends on `from`) *and* `Concept.evidence` (`{prereq_id: quote}`, one entry per `depends_on` id — the source-text justification for that specific prerequisite, not persisted anywhere before this). It also skips any edge that would introduce a cycle when building `depends_on`/`evidence`, since `topological_order` (`graphlib.TopologicalSorter`) assumes a DAG and would otherwise raise unhandled.

`question_generator.py` calls `claude-sonnet-4-6` (with `temperature=0`) once per concept, with a JSON-schema-constrained response asking for a `{concept_id, questions: [{type, question, expected_answer, source_ids}]}` set drawn only from that concept's own evidence anchor (its `summary`), its prerequisites (each with the specific `evidence` quote justifying that dependency, from `Concept.evidence`), and its siblings (other concepts sharing at least one direct prerequisite — concepts with no prerequisites of their own have no siblings). `generate_questions(graph)` mutates every `Concept.questions` in the passed-in graph **in place** (returns `None`) rather than returning a separate map, so the graph stays the single source of truth for a concept's question set; the ingestion router still mirrors each concept's `questions` into the store's separate question index afterward, since `study_session.py` and `routers/questions.py` look questions up there (and diagnostic questions get appended there too). Each question also carries an `expected_answer` — the ideal student response, in prose — and `question_generator.format_answer_notes()` passes it through **verbatim** as `Question.expected_answer_notes` (nothing wrapped around it, `grounding` not appended). That field is what `evaluator.py` labels `RUBRIC:` and grades against, and the bare-prose shape is deliberate: it is exactly what `tests/eval_geval` has always fed the evaluator (its hand-written `golden_answer` fixtures), so production and the suite validating it stay the same kind of input. Prompt rules 8 and 9 govern it — state the substance in full and never defer to context the evaluator cannot see ("as the passage says"), since it receives only the question, this text, and the student's answer; and match the question type (name every required item for `enumeration_completeness`; for `open_ended_example`/`applied_reasoning`, where the correct answer is the student's own and won't appear in the evidence, write what any valid answer must demonstrate rather than one specific example). **This field was a bug fix.** Before it existed, `expected_answer_notes` was the `grounding` quote prefixed "A correct answer is grounded in: ..." — a source passage, which says where a question came from, not what an answer needs. The evaluator was left inventing the decomposition per call (compounding the `temperature=0` non-determinism below), and it was actively wrong for the open-ended types. `tests/eval_geval` never caught it because its fixtures always supplied a proper model answer: the suite was measuring the evaluator under rubric conditions production never produced, which is why its 39/42 was a ceiling rather than a description of real grading. **The model never retypes source text.** `source_passages(concept, by_id, graph)` builds the full list of evidence passages available for a concept — its own summary and each of its `source_quotes` (both `target_concept`), each prerequisite's summary (`prerequisite`) and the quote justifying that dependency (`prerequisite_link`), and each sibling's summary (`sibling`) — each with a stable `s1`/`s2`/… id. The prompt sends that list, the model returns `source_ids` citing which passages a question draws on (rule 7), and `_generate_raw_for_concept()` assembles `RawQuestion.grounding` by joining those exact strings. Verbatim fidelity is therefore structural, not probabilistic. This replaced three rounds of prompt-strengthening (the old rule 7: "treat each passage as atomic… quote every passage in full, never truncate mid-clause") that never held: `write_amplification` reproducibly corrupted the same sentence across live runs even at `temperature=0` — a dropped middle clause, a dropped trailing sentence, an em-dash replaced by a stray artifact — and regressed again the moment other rules were added to the prompt. Citing by id removes the failure mode instead of lowering its odds. `source_passages()` is public specifically so `tests/question_geval` imports it rather than re-deriving the passage list, which is what the suite used to do (mirroring the old `_describe()` by hand) and is exactly the kind of duplication that drifts.

`diagnoser.py` is the one service that is **not** a single structured call — it runs a bounded agentic tool-calling loop over `claude-sonnet-4-6` (design doc: `docs/specs/2026-08-10-diagnoser-agentic-pipeline-design.md`). `diagnose(concept, graph, question, answer, evaluation)` takes the evaluator's `EvaluationResult` as its starting signal (what the answer failed to show) and gets `_MAX_TURNS = 5` round-trips: 4 investigative, then a forced final one where `tool_choice` is pinned to `submit_diagnosis` with only that tool declared, so the loop always ends in a real model judgment rather than a code-side default. Four tools, all executed locally: `get_prereqs` (pure graph lookup — the model calls it on a prerequisite's own id to walk deeper, which is how multi-level drilling happens in one call), `pull_question_from_storage` (reads `Concept.questions`, then `_find_matching_question()` asks `claude-haiku-4-5` whether any candidate actually targets *this* deficiency — a semantic judgment, not keyword overlap), `generate_question` (nested `claude-sonnet-4-6` call), and `submit_diagnosis`. **The certainty gate is code-enforced, not just prompted**: `_accept_diagnosis()` rejects any submission below `"high"` confidence by returning an `is_error` tool_result, so the model cannot end the loop by asserting confidence — and each rejection states its actual reason (bad concept id / bad question id / missing question text), since a generic message would send the model chasing the wrong fix. Parallel tool use is disabled so one tool call = one turn and the budget accounting stays exact. `confidence`/`evidence_basis` are folded into `DiagnosisResult.reasoning` as prose rather than becoming new schema fields.

`evidence_finder.py` (`claude-haiku-4-5`, `temperature=0`, JSON-schema-constrained, same shape as `graph_builder.py`) is the only service that runs *during* graph review rather than in either pipeline proper. `find_evidence(chapter_text, concept)` re-scans the chapter for passages explaining one concept and returns an `EvidenceProposal`; `find_edge_evidence(chapter_text, concept, prereq)` finds the sentence justifying one hand-drawn edge. **Verbatim fidelity is verified, not requested.** `question_generator`'s fix for the same problem — have the model cite ids instead of retyping text — isn't available here, because this pass has to pull text *out* of a document. So `app/services/text_match.py` (`normalize_ws` / `is_verbatim` / `verbatim_only`, shared with `tests/graph_geval`, which used to keep its own copy) filters the model's quotes on the way out: a quote that isn't a contiguous, whitespace-normalized run of the chapter is **discarded, never repaired** — a paraphrase presented as a source quote launders invention into provenance, and there's no safe way to guess which words changed. `found` is then recomputed from what survives rather than trusted from the model, and `dropped` reports the discards, which is what lets the UI distinguish "the chapter doesn't cover this" from "the model paraphrased everything it returned". `_MAX_QUOTES = 4` is asked for in the prompt (rule 6) **and enforced in code**, applied *after* the verbatim filter so a model padding with paraphrases can't squeeze real passages out of the list; trimming is deliberately not counted in `dropped`, which stays a pure "the model invented text" signal. Graded by `tests/evidence_geval` (see Testing) — 9/9 as of the last run, with zero invented evidence and zero non-verbatim quotes.

Key seams:

- **Storage**: `Store` ABC in `backend/app/store/memory_store.py`, two implementations. `get_store()` (`backend/app/store/__init__.py`, lru_cache singleton) returns `PostgresStore` when `settings.database_url` is set, else `InMemoryStore` — so the entire stub-backed test suite runs `InMemoryStore` without any test changes, since tests never set `DATABASE_URL`. Design doc: `docs/specs/2026-08-21-persistent-storage-design.md` (single Postgres instance, no separate graph DB — see that doc's §2 for why a dedicated graph database was rejected for graphs this small). Schema: `documents`, `concepts` (`depends_on`/`evidence`/`source_quotes` as JSONB — nothing queries an edge or a quote independent of a full-graph load), `questions` (`concept_id` FK; the single source of truth for a concept's questions — see the ID-conventions bullet below), `study_sessions`, `history_entries` (`question_id` and `diagnosis_targeted_question_id` FKs into `questions`, never an embedded copy), and `answer_overrides` (see the answer-override bullet below — the one table with **no** FKs). SQLAlchemy (sync) + Alembic; `PostgresStore` (`app/store/postgres_store.py`) opens one short-lived session per method call — no request-scoped session threading. Migrations run automatically on backend startup via a FastAPI `lifespan` hook in `main.py` (a no-op when `database_url` is unset). One deviation from the design doc, found during implementation: `save_questions()` only upserts, it never deletes a row missing from the given list — the doc originally specified full replace-list semantics matching `InMemoryStore`'s raw dict behavior, but `history_entries.question_id`/`.diagnosis_targeted_question_id` have no `ON DELETE` clause, so deleting an already-asked question would violate that foreign key (and would be wrong regardless, since it would destroy real history). Every real call site only ever grows the list, so this is a behavior-preserving narrowing, not a functional change — see `postgres_store.py`'s `save_questions` docstring.
- **Models**: `backend/app/models/schemas.py` is the source of truth; `frontend/src/types/index.ts` mirrors it **by hand — keep them in sync** (includes `AnswerResponse`, the answer-endpoint envelope). The study-session domain model is named `StudySession`/`StudySessionStatus` (not `Session`) specifically so it doesn't collide with a DB session object (e.g. SQLAlchemy's `Session`, now that Postgres is wired in). `Question` is defined before `Concept` in `schemas.py` specifically so `Concept.questions: list[Question]` can reference it directly without a forward ref. `HistoryEntry` carries **two** outcome facts — `evaluation` (the evaluator's own verdict, never rewritten) and `overridden` (whether the student successfully disputed it) — and the effective outcome is their `or`, exposed as the `effective_correct` property; it is a property rather than a field so it isn't serialized and clients combine the same two facts themselves (`frontend/src/lib/conceptProgress.ts`'s `effectiveCorrect`). See the answer-override bullet. The question-id convention lives in `backend/app/models/question_ids.py` rather than in a service — see the ID-conventions bullet.
- **ID conventions (load-bearing)**: concept ids are `{doc_id}:{slug}`, question ids are `{concept_id}:{suffix}` (`q1`, `q2`, `diagnostic1`, `diagnostic2`, …). **Both sides of that convention live in `backend/app/models/question_ids.py`** — minting (`diagnostic_question_id`, used by `diagnoser._next_diagnostic_id`) and reading (`is_diagnostic_question_id`, `has_pipeline_one_question`, and the `DIAGNOSTIC_ID_PATTERN` the Postgres `~` operator uses), mirrored by hand in `frontend/src/lib/questionIds.ts`. It sits in the models layer because the *stores* need it and a Store importing from `app.services` would invert the layering every other module follows (the same constraint that keeps `completed_concepts` in the router). The pattern is anchored — `:diagnostic[0-9]+$`, not a substring test — because `doc:diagnostic-tools:q1` is a pipeline-1 question on a concept called "diagnostic tools", not a probe; `[0-9]` rather than `\d` so the identical string is valid in both Python's `re` and Postgres' regex operator, which is what stops the two implementations drifting. This deliberately gives the suffix a second *reader*, which the study loop otherwise avoids: `study_session._diagnostic_question_ids()` answers "was this served as a probe **in this session**" and rightly consults the session's own diagnosis records, but "did pipeline 1 write this question" has no session to consult (see the graph-colouring bullet). The study-session router (`routers/study_session.py`) resolves an answered question by `question_id.rsplit(":", 1)[0]` → concept's question set. Diagnostic suffixes are **numbered** (`diagnoser._next_diagnostic_id()`) because one concept can be diagnosed more than once in a session with a different gap each time; a fixed `:diagnostic` suffix would collide, and since the router dedupes by id it would silently keep serving the first question's rubric against the second question's prompt. When a diagnostic question is generated, `submit_answer` registers it with a single `store.save_questions(...)` call. That used to also require mutating the suspect's `Concept.questions` on the graph object and re-saving the whole graph — both `Store` implementations now reconstruct `Concept.questions` from the question index on every `get_graph()` call instead (see the Storage bullet above), so a plain `save_questions()` call is enough for a question generated in one diagnostic round to show up as a candidate in a later round on that same concept.
- **Study session list, resume, and delete**: the menu screen (`frontend/src/pages/MenuPage.tsx`) shows every unfinished session via `GET /api/study-session` → `Store.list_unfinished_sessions()`, enriched in the router with `completed_concepts` (`routers/study_session.py`'s `list_study_sessions()` — the store returns the internal `StudySessionSummaryRow`, missing that one field, since computing it needs `topological_order` from `app.services` and a `Store` importing from there would invert the layering every other module follows). **Both halves of the fraction count only *testable* concepts** — ones with at least one pipeline-1 question (`has_pipeline_one_question`) — so the denominator agrees with the node count the student sees drawn: `total_concepts` is narrowed in both stores (`InMemoryStore._testable_concepts`, `PostgresStore._testable_concept_count()`, an `EXISTS` correlated subquery), and `completed_concepts` counts testable concepts positioned before `current_concept_id`. It counts over the **full** topological order and filters, rather than indexing into a pre-filtered list, because `current_concept_id` is not guaranteed testable — `_advance` accepts any concept `get_questions` answers for, including one holding nothing but a diagnostic question minted earlier in the session — and indexing would silently report 0 there. `list_documents()`'s **visibility gate deliberately stays on the raw concept count**: narrowing that too would make a chapter whose every concept came back question-less vanish from the chapter list rather than appear with 0, so it now runs two subqueries, one to gate and one to report. Only unfinished sessions appear — completion drops a session from the list on its own, which is why the original design (`docs/specs/2026-08-29-resume-study-session-design.md`) shipped with no delete affordance at all. `DELETE /api/study-session/{id}` (`docs/specs/2026-09-03-delete-study-session-design.md`) was added later as a deliberate, separate capability on top of that — it removes a session of *any* status, not just a way to prune completed ones. `Store.delete_study_session()` is idempotent (unknown id is a no-op, matching `delete_document`'s contract); `PostgresStore` issues one `DELETE` and relies on `history_entries.study_session_id`'s existing `ON DELETE CASCADE` rather than deleting history rows itself. The frontend confirms before deleting via an inline per-row confirmation (`SessionList.tsx`, one `confirmingId` state value gating at most one row at a time) rather than `window.confirm()` — the feature shipped with the native dialog first, then was replaced with CSS matching the app's own card/badge/button styling once the delete flow itself was validated.
- **Answer override (`POST /api/study-session/{id}/override`)** — design doc `docs/specs/2026-09-18-manual-answer-override-design.md`. The student's channel for "the grader got this wrong", and the only source of real misgrade data the project has (`eval_geval`'s 42 variants are hand-written fixtures). Two things happen: a snapshot of the disagreement is written to `answer_overrides`, and the session takes the same transition a correct answer would. **Capture only as a *corpus*** — nothing reviews the rows as misgrade data, and `Store.list_answer_overrides()` exists but no route exposes it; review is `psql`. The table is no longer write-only from the application's side, though: both stores read it back on every session load to derive `HistoryEntry.overridden` (below).
  - **`answer_overrides` is the one table with no foreign keys**, deliberately inverting the `history_entries` convention ("FK into `questions`, never an embedded copy"). It has to outlive what it describes, and both cascade chains reach it otherwise — `DELETE /api/study-session/{id}` is a live button in `SessionList.tsx` and cascades `history_entries`, while `delete_document` cascades documents → concepts → questions. So the ids are soft strings and `question_prompt`/`expected_answer_notes`/`student_answer`/`evaluator_explanation` are copied in, which also pins the rubric *as it read at grading time* rather than as a join would return it later. Two `test_postgres_store.py` cases assert survival across both deletes.
  - **The evaluator's verdict is never touched — but it no longer stands alone.** `eval_correct` stays `false` with the explanation verbatim, since what the evaluator said is the disputed artifact and rewriting it would destroy the evidence and make a session replay show agreement where there was none. The disagreement rides *beside* it as **`HistoryEntry.overridden`**, derived from `answer_overrides` on every load — `InMemoryStore._mark_overridden` by dict lookup, `PostgresStore.get_study_session` by one query on the soft `(study_session_id, history_seq)` key (not a join: this table deliberately carries no FKs), and `override_answer` sets it on the entry it just wrote so its own response reflects it without a re-read. No migration was needed: `history_seq` is just the entry's index into `history`. **The effective outcome is `evaluation.correct or overridden`** (`HistoryEntry.effective_correct`, mirrored as `effectiveCorrect()` in `frontend/src/lib/conceptProgress.ts`), and that is what `_failed_main_track_attempts` and the graph colouring both read. **This retracts the original design's first consequence**: an overridden attempt no longer counts toward `_MAX_CONCEPT_ATTEMPTS`. It advanced the session exactly as a correct answer would have, so counting it as a failure drove the concept toward being abandoned on the strength of a grade the student had already overturned — and the same misreading leaked outward, painting the concept as an unrectified gap on the graph. See the 2026-09-20 amendment in the design doc §4. This is also the first thing to read `answer_overrides` back; the *corpus* is still unreviewed (below), but the table is no longer write-only from the application's point of view.
  - **Which transition applies is a fact about the overridden *entry*, not the session's current status** — the trap here, and a bug caught by the first test run. After a failed main-track answer the session is already `DIAGNOSING`, so reading `study_session.status` at override time misreads that answer as a prerequisite probe and refuses to advance. The branch instead asks one question — did this answer belong to a concept the session is *not* parked on (`entry.question.concept_id != study_session.current_concept_id`)? That single comparison covers all three non-advancing shapes: a prerequisite probe, the attempt cap having already advanced (where advancing again would silently skip the *next* concept too), and an earlier override having done the same. It deliberately no longer consults `_diagnostic_question_ids()`: reading "was a diagnostic" as "do not advance" is wrong whenever the diagnoser names the answered concept as its own suspect, where handing the concept back re-serves the very question at issue — worst of all here, since the student has just asserted they answered it correctly. A `COMPLETED` session is left completed rather than revived.
  - **Only the session's most recent history entry is overridable** (409 otherwise). The transition depends on where the session is now, so applying it to an older entry would advance from the wrong place; it also makes `history_seq` unambiguous (`len(history) - 1`) with no search.
  - **`save_answer_override()` returns a bool** — the one `save_*` that returns anything. The override appends nothing to history, so the entry it targets stays the newest one and a double-submitted click would pass every check again and advance the session twice. `UNIQUE (study_session_id, history_seq)` is the guard; `PostgresStore` gets the write and the answer from one `ON CONFLICT DO NOTHING ... RETURNING` statement. A re-POST therefore also discards a changed note.
  - Frontend: an "Override Incorrect Answer: My response was correct" button on any incorrect result, opening an inline note panel (the `SessionList.tsx` in-place pattern, not `window.confirm()`). Overrides are only durable with `DATABASE_URL` set — `InMemoryStore` holds them until restart, the same as everything else.
- **Graph progress colouring** — design doc `docs/specs/2026-09-20-graph-progress-coloring-design.md`. The dependency graph is the project's thesis and was inert: `DependencyGraphViz` rendered only on `GraphView` and `ReviewGraphPage`, while the study loop — the one place the structure is being *used* — showed a question card and a result card. `StudySessionPage` already fetched the graph on mount for `conceptName()` and never drew it. So: colour each node by what the session has shown, and render the coloured graph inside the session.
  - **The rule is "last outcome wins"** (`frontend/src/lib/conceptProgress.ts`, `conceptStates()`): a concept's state comes from the most recent history entry that asked about it, with diagnostic and main-track answers counting identically. That is what makes `gap` mean *unrectified* rather than *ever struggled* — a concept diagnosed as the root gap and then answered correctly on its probe is `mastered` from that moment, and one mastered earlier but failed later goes back to `gap`. Diagnostic attribution is free: `diagnoser` sets a targeted question's `concept_id` to the suspect's id. Four states — `current` (wins over everything, since the page names the current concept in prose right above the graph), `mastered`, `gap`, `unreached` — with `gap` also covering the transient where the pending question targets a concept that has no history entry yet (keyed off `pending_question`, **not** the newest diagnosis record: `_MAX_DIAGNOSTIC_CHAIN` can force a return before a diagnosis is ever served, and only a concept actually being asked about should be painted). Nothing is stored or accumulated; history is re-read every render, so a reload reproduces the same colours.
  - **This is deliberately a different number from `completed_concepts`.** That counter is the topological position of `current_concept_id`, so it counts an abandoned concept (attempt cap tripped, answer revealed) as complete; the colouring leaves it amber, because `_advance()` moving past a concept is not evidence of anything. The session list can say "7 of 11" while the graph shows 5 green and 2 amber.
  - **Concepts with no pipeline-1 question are not drawn at all** (`lib/graphFilter.ts`, `withoutUntestableConcepts()`), rather than given a fifth colour: they can never be asked about, so every state would be a false claim about them, and white is the worst of the three because it persists after completion and reads as unfinished work. Three constraints shaped it. (1) **It is a transform the caller applies, never a component default** — `ReviewGraphPage` renders a DRAFT graph where *no* concept has questions yet, so a filter baked into `DependencyGraphViz` (or a flag someone forgets to unset) would blank the one page whose job is editing the graph. (2) **Edges must bridge transitively**: edge rendering resolves each prerequisite with `positions.get(depId)` and draws nothing when it's missing, so dropping `B` from `A → B → C` would erase both edges and leave `C` looking like a root; each survivor's prerequisites are resolved through hidden ones to the nearest surviving ancestors, deduped, with the same cycle guard `layout()`'s `depthOf` carries. A bridged edge drops its `evidence` entry, since there was never a direct edge for a quote to justify. (3) **"Has questions" is the wrong predicate** — both stores rebuild `Concept.questions` from the question index on every `get_graph()`, so the moment the diagnoser probes a hidden concept it would acquire a question, reappear mid-session, and bump the denominator. Drawable is therefore defined over pipeline-1 questions only. Nothing is deleted: the concept stays in the data model (its summary and justifying quote still feed its dependents' question generation via `source_passages()`) and **stays eligible for diagnosis** — a diagnosed gap on a hidden concept simply gets no amber node and is visible only in the "Suspected deficiency" line, the same cost `gap_is_outside_graph` already accepts.
  - **One trap: `conceptName()` must keep reading the *unfiltered* graph.** A diagnosis can name a concept that had no pre-generated questions (the diagnoser mints one for its suspect on the spot), and the page fetches the graph once on mount, so looking names up in the filtered copy would degrade the heading to a raw `{doc_id}:{slug}` id. Filter what is drawn, not what is looked up.
  - `DependencyGraphViz` gains exactly one optional prop, `states?: ReadonlyMap<string, ConceptState>`; omitted, the component renders as before. **Selection and progress use different channels** — progress owns the fill, selection owns the outline — because letting selection recolour the fill hides the very thing a node is coloured for the instant you click it. `unreached`'s swatch *is* the old white/`#b8bede` and a selected node routes through `current`, which *is* the old indigo, so the two uncoloured pages stay pixel-identical by construction rather than by test. A legend is mandatory (four colours with no key is a puzzle) and reads its swatches from the same `STATE_COLORS` table the nodes do. `GraphView` colours from the resumable session it already looks up, fetching that session's detail for its history (the summary row has counts but no history); a failed fetch costs only the colouring and stays off the page-level error path.
  - **The study screen's detail panel omits the question list** `GraphView`'s shows: `GET /api/questions/{concept_id}` returns `expected_answer_notes`, the rubric `evaluator.py` grades against, so rendering a concept's questions mid-session is an answer key for questions not yet asked. It shows state, prerequisites, and an attempt tally (`conceptAttempts`, counting by the same `effectiveCorrect`), with the **summary covered for the concept whose question is currently open** — that summary is the evidence the open question was written from. Keyed off the pending question, not `current_concept_id`, since while diagnosing the concept being asked about is the probe's suspect, not the stalled one.
  - Result card, same pass: it now **restates the question and the student's answer** (the card grades a question that has already been replaced below by the next one, so without them it reads as a verdict on nothing), and shows only the diagnosis's suspect concept — `DiagnosisResult.reasoning` folds in its `evidence_basis`, which restates the evaluator's explanation rendered directly above it, so showing both made every wrong answer read the same gap list twice.
- **Graph review mode (`TextbookUpload.review`, off by default)**: design doc `docs/specs/2026-09-12-human-in-the-loop`. A per-upload choice — a checkbox on the upload form, unticked by default — not a deployment setting: it shipped first as a `GRAPH_EDIT_MODE` env var, which was replaced because gating a user-facing option behind server config meant nobody could reach it without editing `.env` and restarting. When set, `POST /api/textbook` stops after `build_graph()` and saves the chapter as `DocumentStatus.DRAFT` — extraction only, no questions — and `routers/graph_edit.py` accepts edits (add/edit/delete a concept, add/remove a prerequisite) until `POST /api/textbook/{id}/finalize` runs `question_generator` and flips the document to `FINALIZED`. Motivated by `tests/graph_geval`'s standing failures (under-connected edges, over-merged concepts): those are the extractor's ceiling, not a prompt bug, so a human gets to fix the graph before the per-concept generation pass spends a call on each node. **`DRAFT` status is the entire gate** on every editing endpoint (`_draft_graph`), which is why a chapter uploaded without `review` is refused on exactly the same terms as one already approved — both are `FINALIZED`, both 409. Post-finalize editing is deliberately out of scope (design doc §8: questions, sessions and history all reference concepts by id by then). `list_documents()` and `POST /api/study-session/start` both exclude/reject drafts, so a half-reviewed chapter can never be studied. A hand-added prerequisite is scanned for a justifying quote (`evidence_finder.find_edge_evidence`, best-effort — see the evidence bullet below); when the chapter supplies none, or the scan fails, its `Concept.evidence` entry stays `""`, which `question_generator.source_passages()` already skips — the edge contributes the prerequisite's summary but no `prerequisite_link` passage. Cycle safety is the same check both edge paths use: `graph_builder.creates_cycle()`, factored out of the `_reachable` walk `build_graph()` was already doing. Whole-concept deletion is the one mutation `save_graph()` can't express (it only ever upserts), hence `Store.delete_concept()`; every other edit is a plain `save_graph()` of the mutated graph. Frontend: a checkbox on the upload form, and a fourth page, `ReviewGraphPage.tsx`, routed to purely on the upload response's `status` rather than on the request's own flag — the server stays the one authority on which pipeline actually ran.
- **Concept evidence (`Concept.source_quotes`)** — design doc `docs/specs/2026-09-13-concept-evidence-generation.md` (implemented; its "Built as" notes record where the build diverged from the design). Built for hand-added concepts only. Testing the service is specced and built: `docs/specs/2026-09-15-evidence-finder-test-strategy.md` (→ `tests/evidence_geval/`). The rest — measuring whether the evidence actually improves questions, and extending it to extracted concepts — is `docs/specs/2026-09-14-concept-evidence-measurement-and-generalization.md`, **DEFERRED** — its stage 0 premise probe was built, run, and abandoned (see that doc's §3 for what the two runs showed and why it was dropped). The problem: a concept's only "own" evidence used to be its `summary` — 1-2 sentences from `graph_builder` for an extracted concept, a single typed sentence for one added during review — while it inherits rich neighbour context (each prerequisite's summary, the quote justifying each dependency, every sibling's summary). Since `question_generator`'s rules 1 and 4 only permit questions the evidence *fully* supports, the best-supported question is often the neighbour's, which is what `question_geval`'s check 6 measures failing at 0.86. A prompt rule telling the model to stay on target was tried and reverted (target focus 0.86 → 0.85 while evidence basis fell 0.94 → 0.82 — an instruction about what to *prefer* loses to a constraint about what is *possible*), which is why the fix is more target evidence rather than more instructions. `Concept.source_quotes` carries verbatim chapter passages about the concept itself; `source_passages()` emits each as its own `target_concept` passage, so a concept with three good quotes reaches the generator with four passages instead of one.
  - **Filled by proposal, never silently.** `POST /api/graph/{doc_id}/concepts/{concept_id}/evidence` runs `evidence_finder.find_evidence()` and *returns* an `EvidenceProposal`; the reviewer accepts it (whole, in part, or not at all) through the existing `PATCH`, whose `source_quotes` field replaces the whole list. Auto-applying would invert the human-in-the-loop feature this sits inside, and only the reviewer can judge whether a passage is about the concept they meant. Deliberately a **separate request from the add**, so a failed or empty scan costs nothing and `POST .../concepts` stays a fast, LLM-free write; the UI fires it automatically right after an add so there's no way to forget it, plus a "Find evidence" button per row for re-running after a rename.
  - The PATCH **re-checks every quote against the chapter** (`text_match.is_verbatim`) and 422s otherwise. `evidence_finder` is not the only way into the field, and a reviewer "fixing" a typo in a proposed quote turns provenance back into prose — the invariant holds at the write, so everything downstream can treat `source_quotes` as chapter text without re-checking.
  - **`found: false` is a first-class outcome with a user-facing notice.** A chapter often assumes a concept rather than teaching it, which is a legitimate reason to have added it, so `ReviewGraphPage` says *"Could not find evidence for this concept in the chapter"*, names the consequence (its questions come from the summary alone) and both valid responses. It's transient component state, not stored: an empty `source_quotes` can't distinguish "we looked and found nothing" from "nobody has looked". When quotes were dropped as non-verbatim the notice says so, separating "the chapter doesn't cover this" from "the model paraphrased everything".
  - **Not yet measured (DEFERRED) — nobody has shown a concept with `source_quotes` gets better questions than one without.** That is a separate question from "does the scan work", which `tests/evidence_geval` now answers. The follow-on spec sequences it: a premise probe first (~8 calls, seconds — does more target evidence reduce drift at all?), then a full `question_geval` A/B, and only then the generalization to extracted concepts. That last step is expected to go via a **second pass calling `evidence_finder` per concept after `build_graph()`**, not by extending `graph_builder`'s prompt/schema — which leaves `graph_geval` unable to regress and reuses code that is already live-verified. The spec also flags the trap in measuring this: `question_geval`'s `_target_focus_context()` folds every `target_concept`-role passage into the judge's "target" blob, so check 6 could improve without any question improving.

## Stub behavior (intentional, don't "fix")

All five services make real LLM calls now (see Architecture above), so this section is empty. `tests/conftest.py` stubs every one of them (`stub_evaluator` alternates correct/incorrect via a global counter; `stub_graph_builder` returns the old fixed 5-concept calculus graph; `stub_question_generator` sets two templated questions per concept in place; `stub_diagnoser` reproduces the old "pick the first `depends_on` entry" behavior, **falling back to the answered concept itself** when it has no prerequisites — which is load-bearing now that the loop treats a self-diagnosis differently from a prerequisite probe, and is why a test about the prerequisite branch has to walk off the root concept first; `stub_evidence_finder` calls a sentence evidence for a concept when it names that concept, and evidence for an edge when it names both) so `test_flow.py` and friends stay free and deterministic. The evidence stub is crude but exercises the real branch structure rather than hard-coding an outcome — whether a scan finds anything follows from the chapter text a test uploads, and conftest's stub chapter names no concept, so `found: False` is the default everywhere. **An autouse stub makes its own service untestable downstream of it**, so the two places that need the real `evidence_finder` — `tests/test_evidence_finder.py` and `tests/evidence_geval/` — each override `stub_evidence_finder` as a no-op. Forgetting that override is silent: the suite passes while measuring the stub. It bit `test_evidence_finder.py` first (14 failures), which is the cheap version of the same mistake.

  - `tests/question_geval/conftest.py` overrides the parent `stub_question_generator` fixture as a no-op and skips the whole directory if `LLM_API_KEY` is unset, same pattern as the other billed suites.
  - **Checks 4 and 5 grade the answer side**, added after the `expected_answer` bug fix (see Architecture). Until they existed the suite only tested the question-writing half of `question_generator`'s output, while the model-answer half — the entire rubric `evaluator.py` grades against — went untested. (4) *Expected-answer gradeability* (`CaseResult.expected_answer_violations`), fully deterministic, no LLM call: catches shapes the evaluator structurally cannot grade regardless of content — under `MIN_EXPECTED_ANSWER_CHARS = 40`, deferring to context it never receives (`_ANSWER_POINTER_RE`, e.g. "as the passage states"), or a verbatim copy of the `grounding` quote, which is precisely the old bug. Exact-match only on that last one, since a close paraphrase of the evidence is legitimate (for `conceptual_correctness` the ideal answer largely *is* the evidence restated). (5) *Answer quality* (`support.judge_answer_quality()`, `claude-haiku-4-5`), asserted as an aggregate rate ≥ `ANSWER_QUALITY_THRESHOLD = 0.9`: does the `expected_answer` actually and completely answer its own question, consistent with the evidence, standing on its own for a grader that never sees that evidence? The judge prompt carries two explicit allowances so it doesn't penalize correct behavior — describing what any valid answer must demonstrate (right for the open-ended types) and closely restating the evidence (right for `conceptual_correctness`). **Neither has been exercised against the live API yet** — both were added in the same change as the field, so the 3/3 figure below predates them.
  - **Check 6 — target focus** (LLM-judged, `claude-haiku-4-5`, ≥ `TARGET_FOCUS_THRESHOLD = 0.9`): does a question assess the concept it was written for, or a prerequisite/sibling that was only sent as context? Nothing else here asks *which concept* a question is about. It matters twice over: the question wastes one of the target's slots on a concept that already has its own question set, and it corrupts pipeline 2, where "wrong answer on X" is supposed to mean "the gap may be in X's prerequisites" — the signal `diagnoser.py` reasons from. Only concepts that actually have neighbours are scored (nothing to drift onto otherwise). **The judge's context had a harness bug, fixed 2026-09-23:** `_target_focus_context()` filed `prerequisite_link` passages under the neighbour, but those are the chapter's sentences justifying the *target's* dependency and are often its defining sentence ("…storage engines often use additional Bloom filters"), so the judge read questions about the target's own definition as questions about the neighbour. They now go on the target's side. Probed against 17 hand-classified questions before a full run: 7/13 → 15/17 with the judge prompt unchanged, every real off-target question still rejected. Two prompt edits telling the judge to grade only against the evidence were tried and reverted: each fixed a false rejection (the judge demanding Bloom-filter internals the evidence never states) by passing real off-target questions. The probe script is not checked in. **This check fails as of its first live run: 0.86, 4/28 off-target** — e.g. a `write_ahead_log` question asking how many physical writes a logical write causes, which is its sibling `write_amplification`'s question. **A prompt rule was tried and reverted**: a rule 10 saying prerequisites/siblings are context not subject matter moved target focus 0.86 → 0.85 (noise, with the off-target set turning over entirely) while knocking evidence basis 0.94 → 0.82, below threshold — the same destabilization adding rules 8-9 caused, and the reason the prompt is back to its baseline text. Structural read: every drifting concept has a thin summary beside rich neighbour passages, so the most substantive question available is grounded in a neighbour. More target evidence is the fix, not more instructions about neighbours.
  - **Live-run status: 5/5 passing** (224s) — this predates check 6, which now fails (see above), so a current full run is 5/6. Everything below is confirmed against the real API. Getting there took four runs and fixed four distinct defects: (1) `expected_answer_notes` was a source quote rather than a statement of what an answer needs — fixed by the `expected_answer` field; (2) the model corrupted passages it retyped into `grounding` — fixed structurally by having it cite `source_ids` instead (the `write_amplification` em-dash that broke every prior run now arrives verbatim); (3) model answers leaked "The evidence explicitly states…" — fixed by reframing rule 8 around the student's voice; (4) evidence-basis sat at 0.75 then 0.83 against a 0.85 bar, which turned out to be *two* problems: real rule-4 violations (questions asking "why" where the evidence gives an outcome but no mechanism — improved by dropping a speculative `prerequisite_link` hint and tightening rule 4 plus the `conceptual_distinction`/`applied_reasoning` type descriptions, at no cost to type recall) and a miscalibrated judge (see check 3 above — it held all five types to a restatement bar, which `open_ended_example` and `applied_reasoning` can never meet by design).
  - **A green run is not self-evidently healthy here, so the suite always prints its metrics** (`pytest_terminal_summary` in `tests/question_geval/conftest.py`, reading `score_case`'s cache so it costs nothing and stays quiet when the suite skips). A passing assertion prints nothing, so the 5/5 run above left its actual rates unknown — and for the LLM-judged checks an exact 1.00 would mean the judge had stopped discriminating, which is indistinguishable from a healthy pass without the number. The summary also names every question the judges rejected, so a green run still shows you what to eyeball.
  - **Recalibrating a judge to make a test pass is a real hazard, so the type-awareness change was probed directly** rather than trusted because the suite went green: five questions from the failing run were re-judged in isolation (~5 cheap calls, no full run). Two still came back not-grounded, so the constructive-type band is not a blanket pass. The probe also corrected the triage twice — `memtable`'s burst-of-writes question, filed as a genuine violation, is now grounded on the defensible reading that the evidence does state the mechanism (memtable flushes to an SSTable past its threshold) and the old judge was demanding a deeper answer than the question asked; while `write_amplification`, predicted to be rescued, still fails. Rerun that probe rather than the whole suite when touching judge prompts.
  - Grounding-fidelity history, three prompt fixes deep before the structural fix retired the problem: (1) the first run found `question_generator.py` truncating a second evidence source mid-clause on `conceptual_distinction` questions (which combine two sources) — fixed by adding rule 7 to `_SYSTEM_PROMPT` ("treat each passage as atomic... quote every passage in full, never truncate mid-clause"); (2) re-running surfaced that the original sentence-split-based grounding check was itself flaky against the model's (delimiter-varying) multi-quote joining style — replaced with a truncation+coverage check; (3) `write_amplification` still reproducibly failed after both, with a *different* manifestation each run despite `temperature=0` (dropping a middle clause; dropping a trailing sentence; substituting an em-dash with a stray artifact) — all centered on one sentence whose content overlaps between the target's own summary and the `lsm_tree` prerequisite's evidence. Rule 7 was strengthened again and held for two runs, then regressed the moment rules 8-9 were added. - **`backend/tests/diagnoser_geval/`** — a regression suite for `diagnoser.py`, built on 9 hand-authored diagnosis cases over the same Case 3 graph the other suites use (concept shape imported from `tests/question_geval/golden.py`, so the three cannot disagree about the case; `golden._validate()` runs at import and fails loudly if a fixture references an unknown concept or claims a hop distance the graph doesn't support). Shaped differently from the other suites because the diagnoser is an agentic loop rather than a single call, which breaks three of their assumptions:
  - **The output isn't the whole behavior.** That it investigated before concluding, that the certainty gate held, that it stayed in budget — none of it appears in `DiagnosisResult`. Hence `diagnoser._diagnose_with_trace()`, the internal seam (same pattern as `_extract_raw_graph()` / `_generate_raw_for_concept()`) returning a `DiagnosisTrace` of turns used, tool calls, rejected submissions, concepts inspected, and whether the final turn was forced. Worth having regardless of tests: without it a diagnosis that burned five turns and three rejections looks identical to a clean first-turn hit in production logs too.
  - **Ground truth is interpretive**, unlike graph_geval's concepts (objectively in the text) or question_geval's closed `type` vocabulary. So each case carries `acceptable_suspects` (a set — any is a pass), `preferred_suspect` (reported, never asserted), and `forbidden_suspects` (zero tolerance). The forbidden sets carry most of the discriminating power: several cases have the student demonstrate mastery of a neighbouring concept, so naming it contradicts the evidence rather than merely being suboptimal.
  - **Trajectories vary more than outputs** — `temperature=0` pins each call, but a different tool choice on turn 2 changes everything downstream — so metrics are aggregate rates, not per-case assertions.
  - Five checks in three tiers: (1) invariants, deterministic and zero-tolerance — no answer leak (the suspect's summary must not surface in the question, checked as an exact substring *and* an 8-word shared run via `_leaked_span`, since a paraphrase leaks just as well; this was called load-bearing in the original stub's docstring and had never been checked), suspect reachable from the answered concept via `depends_on`, question/id/notes well-formed, budget respected; (2) accuracy against `acceptable_suspects` plus zero `forbidden_suspects`, **reported split by hop depth** — the number that says whether the agentic design beats the old `depends_on[0]` stub; (3) two `claude-haiku-4-5` judges — does the targeted question actually probe its suspect, and is the reasoning evidence-backed rather than plausible-sounding (the certainty requirement made observable, since the code gate can only enforce that the model *claimed* high confidence).
  - `tests/diagnoser_geval/probe.py` is the iteration tool, and it is the thing to reach for before a full run. `probe case <name>` runs one case and prints its whole trajectory; `probe judges` re-checks both judges against fixed good and bad inputs. It has already earned itself twice — catching an ambiguous word in a judge prompt ("do not *reward* restating the concept" read as *penalize*), and a harness bug where `judge_reasoning_quality` compared the model's quotes against `suspect.evidence` when evidence *about* a concept actually lives on its dependents (`Concept.evidence` maps a concept's own prerequisites to their justifying quotes, which is what `get_prereqs` surfaces). Re-run `probe judges` after any judge-prompt edit: a judge that stops discriminating makes the suite green while measuring nothing, and at exactly 1.00 that is indistinguishable from a healthy pass.
  - Loop mechanics are **not** here — they're deterministic against a fake client, so they live in the free `tests/test_diagnoser_loop.py` (turn budget, forced final turn, certainty-gate rejection, per-reason rejection messages, error recovery, id incrementing). `tests/test_diagnoser_geval_wiring.py` is the free smoke test for this suite, same role as question_geval's: it drives `score_all()` with fakes so a name only referenced inside the billed path fails in 0.03s instead of mid-run.
  - `pytest_terminal_summary` prints every metric plus a per-case trajectory table on pass as well as failure, for the same reason question_geval does.
  - **As of the last full run: 6/6 passing** over 9 cases — accuracy 0.89, 0 forbidden, 0 invariant violations, 0 spurious outside-graph disclosures, question relevance 0.89, reasoning grounded 1.00, every hop depth scoring (0/1/2/3). Multi-hop drilling works: the 2-hop and 3-hop cases both land correctly, which is what says the agentic loop earns its cost over the old `depends_on[0]` stub.
  - **The most useful finding came from the trajectory, not the assertions.** The first run passed 5/5 while **5 of 8 cases hit the forced final turn** — spending the entire budget on `get_prereqs` and never converging, so they never reached `pull_question_from_storage` or `generate_question` at all. Two lines of `_SYSTEM_PROMPT` were pushing toward it ("the root gap is often deeper than one hop"; "spend them investigating"), reworded so stopping early is the goal rather than a compromise: **forced-final went 5/8 → 0/8**, mean turns 4.4 → 3.6, accuracy unchanged at 0.88. That also settles `_MAX_TURNS`: 5 turns was never the constraint, the prompt was. Note this is only visible because the suite prints trajectory stats on a green run — the assertions passed identically before and after.
  - The tradeoff is worth knowing: less investigation means **more self-diagnosis**. Both post-change degradations are that one effect — `hash_index` moved from `append_only_log` to `hash_index` (still acceptable, no longer preferred), and `wal_missing_btree_pages` names `write_ahead_log` rather than tracing to `b_tree` (a stable MISS across both runs, deliberately left as a miss: a diagnoser that answers "the concept itself" for non-leaf concepts has stopped doing its job). More probing buys deeper tracing and costs turns; that is the lever.
  - **The general-knowledge escape hatch is wired but empirically unexercised.** When no concept in the graph explains the deficiency the diagnoser may diagnose from background knowledge instead (system prompt rule 3), setting `gap_is_outside_graph` on `submit_diagnosis` and passing `allow_general_knowledge` to `generate_question` so the nested generator's evidence-only rule is relaxed for that call. The disclosure leads `DiagnosisResult.reasoning`, which is what the answer endpoint returns to the student — reusing the channel that already carries the low-confidence note, so nothing new is plumbed through the API or the frontend types. Only the false-positive direction is asserted (`spurious_disclosures`): the notice is user-visible, so a spurious one is noise that trains students to ignore a warning meant to be rare, while a missed one merely leaves prior behavior in place. On the run above **recall was 0.00** — the one case built for it (`hash_lookup_is_background_knowledge`) was diagnosed as `hash_index` directly instead. That is ambiguous between the prompt rule not landing and the fixture's premise being wrong (the chapter does say "in-memory hash map", so reading that error as a `hash_index` gap is defensible), and one case is too thin to tell. Treat the positive path as untested.
  - Thresholds are deliberately loose, not yet tightened to observed performance. Two runs both scored exactly 7/8 accuracy, so raising `ACCURACY_THRESHOLD` from 0.75 to 0.85 would leave zero headroom — with 8 cases each worth 12.5%, one trajectory flip turns the suite red. The real regression detector is the per-case table in the terminal summary; the threshold only catches a collapse.

- **`backend/tests/evidence_geval/`** — a regression suite for `evidence_finder.py`, over the same Case 3 chapter (source text and concept ids imported from `tests/graph_geval/golden.py`, so a fourth suite can't disagree with the other three about the case). Design doc: `docs/specs/2026-09-15-evidence-finder-test-strategy.md`. **Shaped differently from all three others, and that is the point:**
  - **`evidence_finder` is the one *extractive* service** — every other one generates text with no ground truth to diff against, which is why their suites lean on a judge and carry the standing "a judge that stops discriminating measures nothing" hazard. Here the right answer is *a set of spans in a document the test already holds*, so span accuracy, verbatim fidelity, found-precision, contiguity and cap adherence are all arithmetic. Only two of the checks call an LLM. That also makes it the cheapest of the five (Haiku only, ~165s) and the most stable: a judge's opinion of a varying output varies twice over; a substring check over a varying output varies once.
  - **The headline check is span accuracy**, and it exists because a quote can be verbatim, contiguous, genuinely in the chapter — and *about a neighbour*. That passes every gate the service has, and feeds `question_generator` exactly the neighbour-weighted evidence `source_quotes` was built to remove. `golden.py` hand-labels the chapter regions defensibly about each concept as **verbatim anchor strings resolved to offsets at import** (integer offsets rot silently when the source is reflowed; an anchor fails loudly), and every returned quote is located and tested for containment.

  - **Negative fixtures are per-chapter, not global.** Six concepts verified absent from Case 3 by substring search (`replication`, `partitioning`, `consensus`, `secondary_index`, `transaction`, `column_oriented_storage`) — several of which are concepts in *other* golden cases, so reusing this list against another chapter would assert `found: false` for something that chapter teaches. An early draft proposed `b_tree`, which Case 3 teaches in full; `_validate()` re-checks every negative at import.

The four surviving off-target quotes were spot-checked and are genuine model errors (`log_segment` twice returning compaction's passage, `sstable` the memtable paragraph, `b_tree` the WAL paragraph) — failure mode #1 at ~17%, which nothing previously measured.
  - **The first run's 0.70 was partly the fixtures' fault**, not the model's: three of six off-target quotes were labelling gaps (the chapter's closing LSM-tree/B-tree comparison was labelled for nobody; one anchor was a single sentence where the model returned it plus its continuation, failing containment). Triage each failure against the raw output before believing a rate — the same warning the other suites carry.
  - `tests/evidence_geval/probe.py` — `probe case <concept>` runs one concept and locates every quote against its labelled regions (it takes negative fixtures too, e.g. `probe case replication`); `probe judges` re-checks both judges against fixed good and bad inputs. **It has already earned itself twice, in opposite directions.** It first rejected a fixture of mine that expected "This in-memory tree is sometimes called a memtable" to be explanatory — the judge was right, "This" has no antecedent inside the quote, so the fixture was corrected rather than the prompt loosened. ## Docker gotchas

- `docker-compose.override.yml` (auto-merged) is dev mode: vite dev server (Dockerfile `dev` target), `uvicorn --reload`, bind mounts. It uses `ports: !override` to replace (not append to) the base port mapping, and a **distinct image tag** (`comprehension-agent-frontend-dev`) so dev/prod builds don't clobber each other — if the frontend serves nothing on :5173, a stale image from the other mode is the likely cause; rebuild with `--build`.
- Prod frontend: nginx serves `dist/` and proxies `/api` → `backend:8000` (`frontend/nginx.conf`). Dev: vite proxies `/api` using `BACKEND_URL` env var (`vite.config.ts`).
- Backend `env_file: .env` means compose fails without `.env` — copy from `.env.example`.
- `postgres`'s host port is `5433`, not the standard `5432` — chosen to avoid colliding with a locally-installed Postgres. Published as `127.0.0.1:5433:5432`, not the bare `"5433:5432"` form — the bare form binds `0.0.0.0`, reachable from anyone else on the same network using the fixed dev credentials (`comprehension_agent`/`devpassword`) baked into `docker-compose.yml`/`.env.example`; loopback-only closes that off without changing anything for local use. Only matters for connecting from the host (native `uvicorn`, `psql`, a GUI client); inside the compose network the `backend` service reaches it as `postgres:5432` (the container-internal port, unaffected by the host-side binding), via a `DATABASE_URL` override in `docker-compose.yml` that takes precedence over whatever `.env` provides through `env_file`. Because `postgres` is a compose service now, plain `docker compose up` (no args) starts it even though nothing depends on it yet — harmless, but a behavior change from before this existed.

## Not built yet (deliberate)

No auth — which is why graph review is offered to whoever is uploading rather than to an "instructor" role: anyone using the app can tick the box and edit the graph they just extracted. Persistent storage (`PostgresStore`, see the Storage bullet above) is built but opt-in — set `DATABASE_URL` to use it, unset it and the app is exactly as before (`InMemoryStore`, nothing to run). Review mode is opt-in per upload; its Postgres half (the `documents.status` column, migration `c1e4a9b7f20d`) has been applied to a real database and `test_postgres_store.py` passes 30/30 against one. All four pipeline services (`graph_builder.py`, `question_generator.py`, `evaluator.py`, `diagnoser.py`) make real LLM calls and have live regression suites. `evidence_finder.py` has one too now (`tests/evidence_geval/`, 9/9 — see Testing). What remains unmeasured for it is a different question: whether the evidence it finds actually produces better questions, which is `docs/specs/2026-09-14-concept-evidence-measurement-and-generalization.md` (DEFERRED). The answer-override feature captures misgrades but nothing reviews them *as a corpus*: there is no read endpoint, no UI, and no tuning loop — it is read with `psql` (design doc §8). The rows are read back by the app itself, but only to resolve `HistoryEntry.overridden` on load. Per-learner mastery across sessions is also unbuilt: the graph colouring reads one session's history, and there is no auth to hang a learner on. CI (`.github/workflows/ci.yml`) runs backend pytest against a real ephemeral Postgres service (so `test_postgres_store.py` runs for real in CI, migrated fresh each run) plus the frontend unit tests (`npm test`) and build — it does not run any of the five billed `geval` suites, which stay skipped since CI sets no `LLM_API_KEY`.

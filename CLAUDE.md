# CLAUDE.md

Adaptive concept tutor: ingests textbook chapters, builds a concept dependency graph, and runs a Q&A loop that traces wrong answers back to the prerequisite concept at fault. `graph_builder.py` (pipeline 1, step 2), `question_generator.py` (pipeline 1, step 3), `evaluator.py` (pipeline 2, step 2), and `diagnoser.py` (pipeline 2, steps 3-5) all make real LLM calls.

## Architecture

Two pipelines in `backend/app/services/`:

1. **Pre-questioning** (per uploaded chapter): `POST /api/textbook` → `graph_builder.build_graph()` (real LLM call) → `question_generator.generate_questions()` (real LLM call, one per concept), all synchronous, results saved to the store.
2. **Diagnostic loop** (per study session): `POST /api/study-session/{id}/answer` → `evaluator.evaluate()`. Correct → advance `current_concept_id` in topological order. Incorrect → `diagnoser.diagnose()` returns a targeted question probing a prerequisite; study session status becomes `diagnosing`. Both `evaluator.evaluate()` and `diagnoser.diagnose()` are real.

`evaluator.py` calls `claude-haiku-4-5` via the Anthropic SDK with a JSON-schema-constrained response (`_OUTPUT_SCHEMA`) grading the student's answer against `question.expected_answer_notes`. It's the template `graph_builder.py` and `question_generator.py` followed (`diagnoser.py` needed a different shape — see below). Known issue: the `temperature=0` call parameter is currently commented out, which means grading is **not deterministic** — the same question/answer pair can flip between `correct: true/false` across calls. Re-enabling it is recommended; the `tests/geval` suite (see Testing below) is what surfaced this.

`graph_builder.py` calls `claude-haiku-4-5` (with `temperature=0`, unlike `evaluator.py`) with a JSON-schema-constrained response asking for `{concepts: [{id, label, summary}], edges: [{from, to, evidence}]}` extracted from the chapter text. `_extract_raw_graph()` does the LLM call + parsing + dedup and returns that raw shape (still carrying each edge's `evidence` quote, un-namespaced ids) — it's an internal seam, not stable public API, kept separate so `tests/graph_geval` can grade edge evidence directly. `build_graph()` folds `edges` into each `Concept.depends_on` (`to` depends on `from`) *and* `Concept.evidence` (`{prereq_id: quote}`, one entry per `depends_on` id — the source-text justification for that specific prerequisite, not persisted anywhere before this). It also skips any edge that would introduce a cycle when building `depends_on`/`evidence`, since `topological_order` (`graphlib.TopologicalSorter`) assumes a DAG and would otherwise raise unhandled.

`question_generator.py` calls `claude-sonnet-4-6` (with `temperature=0`) once per concept, with a JSON-schema-constrained response asking for a `{concept_id, questions: [{type, question, expected_answer, source_ids}]}` set drawn only from that concept's own evidence anchor (its `summary`), its prerequisites (each with the specific `evidence` quote justifying that dependency, from `Concept.evidence`), and its siblings (other concepts sharing at least one direct prerequisite — concepts with no prerequisites of their own have no siblings). `generate_questions(graph)` mutates every `Concept.questions` in the passed-in graph **in place** (returns `None`) rather than returning a separate map, so the graph stays the single source of truth for a concept's question set; the ingestion router still mirrors each concept's `questions` into the store's separate question index afterward, since `study_session.py` and `routers/questions.py` look questions up there (and diagnostic questions get appended there too). Each question also carries an `expected_answer` — the ideal student response, in prose — and `question_generator.format_answer_notes()` passes it through **verbatim** as `Question.expected_answer_notes` (nothing wrapped around it, `grounding` not appended). That field is what `evaluator.py` labels `RUBRIC:` and grades against, and the bare-prose shape is deliberate: it is exactly what `tests/geval` has always fed the evaluator (its hand-written `golden_answer` fixtures), so production and the suite validating it stay the same kind of input. Prompt rules 8 and 9 govern it — state the substance in full and never defer to context the evaluator cannot see ("as the passage says"), since it receives only the question, this text, and the student's answer; and match the question type (name every required item for `enumeration_completeness`; for `open_ended_example`/`applied_reasoning`, where the correct answer is the student's own and won't appear in the evidence, write what any valid answer must demonstrate rather than one specific example). **This field was a bug fix.** Before it existed, `expected_answer_notes` was the `grounding` quote prefixed "A correct answer is grounded in: ..." — a source passage, which says where a question came from, not what an answer needs. The evaluator was left inventing the decomposition per call (compounding the `temperature=0` non-determinism below), and it was actively wrong for the open-ended types. `tests/geval` never caught it because its fixtures always supplied a proper model answer: the suite was measuring the evaluator under rubric conditions production never produced, which is why its 39/42 was a ceiling rather than a description of real grading. **The model never retypes source text.** `source_passages(concept, by_id, graph)` builds the full list of evidence passages available for a concept — its own summary (`target_concept`), each prerequisite's summary (`prerequisite`) and the quote justifying that dependency (`prerequisite_link`), and each sibling's summary (`sibling`) — each with a stable `s1`/`s2`/… id. The prompt sends that list, the model returns `source_ids` citing which passages a question draws on (rule 7), and `_generate_raw_for_concept()` assembles `RawQuestion.grounding` by joining those exact strings. Verbatim fidelity is therefore structural, not probabilistic. This replaced three rounds of prompt-strengthening (the old rule 7: "treat each passage as atomic… quote every passage in full, never truncate mid-clause") that never held: `write_amplification` reproducibly corrupted the same sentence across live runs even at `temperature=0` — a dropped middle clause, a dropped trailing sentence, an em-dash replaced by a stray artifact — and regressed again the moment other rules were added to the prompt. Citing by id removes the failure mode instead of lowering its odds. `source_passages()` is public specifically so `tests/question_geval` imports it rather than re-deriving the passage list, which is what the suite used to do (mirroring the old `_describe()` by hand) and is exactly the kind of duplication that drifts.

`diagnoser.py` is the one service that is **not** a single structured call — it runs a bounded agentic tool-calling loop over `claude-sonnet-4-6` (design doc: `docs/specs/2026-08-10-diagnoser-agentic-pipeline-design.md`). `diagnose(concept, graph, question, answer, evaluation)` takes the evaluator's `EvaluationResult` as its starting signal (what the answer failed to show) and gets `_MAX_TURNS = 5` round-trips: 4 investigative, then a forced final one where `tool_choice` is pinned to `submit_diagnosis` with only that tool declared, so the loop always ends in a real model judgment rather than a code-side default. Four tools, all executed locally: `get_prereqs` (pure graph lookup — the model calls it on a prerequisite's own id to walk deeper, which is how multi-level drilling happens in one call), `pull_question_from_storage` (reads `Concept.questions`, then `_find_matching_question()` asks `claude-haiku-4-5` whether any candidate actually targets *this* deficiency — a semantic judgment, not keyword overlap), `generate_question` (nested `claude-sonnet-4-6` call), and `submit_diagnosis`. **The certainty gate is code-enforced, not just prompted**: `_accept_diagnosis()` rejects any submission below `"high"` confidence by returning an `is_error` tool_result, so the model cannot end the loop by asserting confidence — and each rejection states its actual reason (bad concept id / bad question id / missing question text), since a generic message would send the model chasing the wrong fix. Parallel tool use is disabled so one tool call = one turn and the budget accounting stays exact. `confidence`/`evidence_basis` are folded into `DiagnosisResult.reasoning` as prose rather than becoming new schema fields.

Key seams:

- **Storage**: `Store` ABC in `backend/app/store/memory_store.py`, two implementations. `get_store()` (`backend/app/store/__init__.py`, lru_cache singleton) returns `PostgresStore` when `settings.database_url` is set, else `InMemoryStore` — so the entire stub-backed test suite runs `InMemoryStore` without any test changes, since tests never set `DATABASE_URL`. Design doc: `docs/specs/2026-08-21-persistent-storage-design.md` (single Postgres instance, no separate graph DB — see that doc's §2 for why a dedicated graph database was rejected for graphs this small). Schema: `documents`, `concepts` (`depends_on`/`evidence` as JSONB — nothing queries an edge independent of a full-graph load), `questions` (`concept_id` FK; the single source of truth for a concept's questions — see the ID-conventions bullet below), `study_sessions`, `history_entries` (`question_id` and `diagnosis_targeted_question_id` FKs into `questions`, never an embedded copy). SQLAlchemy (sync) + Alembic; `PostgresStore` (`app/store/postgres_store.py`) opens one short-lived session per method call — no request-scoped session threading. Migrations run automatically on backend startup via a FastAPI `lifespan` hook in `main.py` (a no-op when `database_url` is unset). One deviation from the design doc, found during implementation: `save_questions()` only upserts, it never deletes a row missing from the given list — the doc originally specified full replace-list semantics matching `InMemoryStore`'s raw dict behavior, but `history_entries.question_id`/`.diagnosis_targeted_question_id` have no `ON DELETE` clause, so deleting an already-asked question would violate that foreign key (and would be wrong regardless, since it would destroy real history). Every real call site only ever grows the list, so this is a behavior-preserving narrowing, not a functional change — see `postgres_store.py`'s `save_questions` docstring.
- **Models**: `backend/app/models/schemas.py` is the source of truth; `frontend/src/types/index.ts` mirrors it **by hand — keep them in sync** (includes `AnswerResponse`, the answer-endpoint envelope). The study-session domain model is named `StudySession`/`StudySessionStatus` (not `Session`) specifically so it won't collide with a future DB session object (e.g. SQLAlchemy's `Session`) once Postgres is wired in. `Question` is defined before `Concept` in `schemas.py` specifically so `Concept.questions: list[Question]` can reference it directly without a forward ref.
- **ID conventions (load-bearing)**: concept ids are `{doc_id}:{slug}`, question ids are `{concept_id}:{suffix}` (`q1`, `q2`, `diagnostic1`, `diagnostic2`, …). The study-session router (`routers/study_session.py`) resolves an answered question by `question_id.rsplit(":", 1)[0]` → concept's question set. Diagnostic suffixes are **numbered** (`diagnoser._next_diagnostic_id()`) because one concept can be diagnosed more than once in a session with a different gap each time; a fixed `:diagnostic` suffix would collide, and since the router dedupes by id it would silently keep serving the first question's rubric against the second question's prompt. When a diagnostic question is generated, `submit_answer` registers it with a single `store.save_questions(...)` call. That used to also require mutating the suspect's `Concept.questions` on the graph object and re-saving the whole graph — both `Store` implementations now reconstruct `Concept.questions` from the question index on every `get_graph()` call instead (see the Storage bullet above), so a plain `save_questions()` call is enough for a question generated in one diagnostic round to show up as a candidate in a later round on that same concept.
- **Study session list, resume, and delete**: the menu screen (`frontend/src/pages/MenuPage.tsx`) shows every unfinished session via `GET /api/study-session` → `Store.list_unfinished_sessions()`, enriched in the router with `completed_concepts` (`routers/study_session.py`'s `list_study_sessions()` — the store returns the internal `StudySessionSummaryRow`, missing that one field, since computing it needs `topological_order` from `app.services` and a `Store` importing from there would invert the layering every other module follows). Only unfinished sessions appear — completion drops a session from the list on its own, which is why the original design (`docs/specs/2026-08-29-resume-study-session-design.md`) shipped with no delete affordance at all. `DELETE /api/study-session/{id}` (`docs/specs/2026-09-03-delete-study-session-design.md`) was added later as a deliberate, separate capability on top of that — it removes a session of *any* status, not just a way to prune completed ones. `Store.delete_study_session()` is idempotent (unknown id is a no-op, matching `delete_document`'s contract); `PostgresStore` issues one `DELETE` and relies on `history_entries.study_session_id`'s existing `ON DELETE CASCADE` rather than deleting history rows itself. The frontend confirms before deleting via an inline per-row confirmation (`SessionList.tsx`, one `confirmingId` state value gating at most one row at a time) rather than `window.confirm()` — the feature shipped with the native dialog first, then was replaced with CSS matching the app's own card/badge/button styling once the delete flow itself was validated.
- Concept ordering uses `graphlib.TopologicalSorter` (`graph_builder.topological_order`).

## Stub behavior (intentional, don't "fix")

All four services make real LLM calls now (see Architecture above), so this section is empty. `tests/conftest.py` stubs every one of them (`stub_evaluator` alternates correct/incorrect via a global counter; `stub_graph_builder` returns the old fixed 5-concept calculus graph; `stub_question_generator` sets two templated questions per concept in place; `stub_diagnoser` reproduces the old "pick the first `depends_on` entry" behavior) so `test_flow.py` and friends stay free and deterministic.

## Testing

- **Stub-backed tests** (`backend/tests/test_flow.py`, `test_health.py`): free, fast, no API key needed. `tests/conftest.py` monkeypatches `evaluator.evaluate`, `graph_builder.build_graph`, `question_generator.generate_questions`, and `diagnoser.diagnose` with deterministic stubs (autouse fixtures) so these never hit the real API. `test_flow.py` runs against whichever backend `get_store()` currently resolves to — `InMemoryStore` normally, `PostgresStore` if `DATABASE_URL` happens to be set — so `test_diagnostic_question_is_registered_in_both_places` (the regression test for the questions-duplication bug, see the Storage bullet above) is confirmed passing against the real schema, not just the in-memory one.
- **`backend/tests/test_postgres_store.py`** — real Postgres, no LLM calls (so it's free to run cost-wise, unlike the `geval` suites below — only real infrastructure, not a real API key, gates it). Skips if `DATABASE_URL` is unset, same opt-in pattern as the `geval` suites. `docker compose up -d postgres` first, then run against a real, already-migrated database — no testcontainers. An autouse fixture truncates all five tables before every test; a second autouse fixture (`_require_database`) has to run *before* it, or the truncate fixture's `get_engine()` call fails on an empty `DATABASE_URL` instead of skipping cleanly — fixture load-order across two autouse fixtures at the same scope isn't guaranteed unless one explicitly depends on the other. Covers round-trips for every entity, `save_questions()`'s upsert-only semantics (deliberately never deletes — see the Storage bullet), and specifically the join behavior that's the whole point of this schema: a question saved via `save_questions()` alone shows up in the next `get_graph()` with no companion write.
- **`backend/tests/geval/`** — a G-Eval regression suite (via [DeepEval](https://github.com/confident-ai/deepeval)) that runs the *real* `evaluator.evaluate()` against the 10 questions/42 answer variants in `tests/geval_test_suite.md`, then scores the evaluator's explanation against the golden answer using a `GEval` metric judged by a separate model (`claude-opus-4-5`, deliberately different/stronger than the `claude-haiku-4-5` evaluator under test, to avoid a model grading its own homework).
  - Organized one file per chapter (`test_ch1.py`…`test_ch8.py`), one test function per question/answer-variant pair.
  - `criteria.py` holds each question's G-Eval `criteria` (copied from the markdown) and `evaluation_steps`, hand-derived and **hardcoded** — GEval would otherwise regenerate steps via an LLM call on every run, making the rubric non-deterministic across runs. If a question's criterion changes, regenerate its steps by hand and update `criteria.py`; don't let evaluation_steps go unset.
  - `tests/geval/conftest.py` overrides the parent `stub_evaluator` fixture as a no-op (real calls needed) and skips the whole directory if `LLM_API_KEY` is unset, so CI (which has no key) stays green.
  - **Makes real, billed Anthropic API calls** — roughly $0.35–0.45 and 5-6 minutes for a full run (Opus judge calls dominate cost). Don't run this suite reflexively; it's for validating changes to `evaluator.py`'s prompt/model.
  - As of the last full run: 39/42 passing. The 3 known failures are real evaluator leniency gaps (not suite bugs) — see git history around the `evaluator implementation done` / `g-eval test suite` commits for details.
- **`backend/tests/graph_geval/`** — a structural regression suite for `graph_builder.py`, built from the 4 DDIA excerpts in `tests/graph_golden_set.md` (hand-curated expected concepts/edges/"forbidden" ideas per case). Different shape than `tests/geval/` since the output under test is a graph, not free text:
  - Runs the real `graph_builder._extract_raw_graph()` on each case's source text, then aligns the extracted concepts to the golden concepts by meaning via a judge LLM call (`claude-sonnet-4-5` — cheaper than Opus since this is structural matching, not open-ended judgment; still stronger than the `claude-haiku-4-5` extractor under test). Edge quoted-evidence is checked deterministically (no LLM call): every edge's `evidence` must be a verbatim (whitespace-normalized) substring of the source text.
  - `golden.py` hardcodes each case's expected concepts/edges/forbidden-ideas; source text itself is *not* duplicated there — it's parsed straight out of `graph_golden_set.md`'s fenced code blocks so it can never drift from what the evidence check validates against.
  - One file per case (`test_case1.py`…`test_case4.py`), 4 tests each: concept recall ≥ 0.8, zero forbidden-idea leaks, edge recall ≥ 0.6, all edge evidence verbatim. `support.score_case()` is `lru_cache`d per case so those 4 assertions share one extraction call + one alignment call rather than re-running the real API per assertion.
  - `tests/graph_geval/conftest.py` overrides the parent `stub_graph_builder` fixture as a no-op and skips the whole directory if `LLM_API_KEY` is unset, same pattern as `tests/geval/`.
  - As of the first full run: 8/16 passing. Spot-checked each failure against the raw model output — none are harness bugs, all are genuine gaps in current `graph_builder.py` output: (1) edge recall is the weakest area — the model frequently extracts the right concepts but under-connects them (e.g. Case 4's `oltp → olap → data_warehouse` backbone edges are missing even though all three concepts matched); (2) some individually quiz-worthy sub-concepts (Case 2's `dirty_read`/`dirty_write`/`read_skew`/`race_condition`) are getting folded away — likely a side effect of the "be strict about what counts as a concept" prompt tightening earlier in this suite's development; (3) two forbidden-idea leaks (Case 2's "Weak Isolation Levels" and Case 3's generic "Index" each got their own node despite the source text treating them as folded-in/anti-pattern); (4) two edges with paraphrased-not-verbatim evidence quotes. Not yet triaged into "prompt needs tuning" vs. "golden expectations too strict" — see conversation/PR history for the analysis.
- **`backend/tests/question_geval/`** — a regression suite for `question_generator.py`, covering Case 3 — Storage Engines (all 11 concepts) from `tests/graph_golden_set.md`. Unlike `tests/graph_geval/`, no judge LLM call is needed for alignment: the input graph is constructed directly (concept ids/labels/edges reused from `tests/graph_geval/golden.py` so the two suites can't drift on graph shape; a runtime assertion in `build_graph()` guards against drift), so the generator's output is already keyed to known concept ids and the `type` field is a closed vocabulary — no fuzzy matching required.
  - Runs the real `question_generator._generate_raw_for_concept()` per concept (the same "internal seam, not stable public API" pattern as `graph_builder._extract_raw_graph()` — exposes each raw `{type, question, expected_answer, source_ids, grounding}` before `generate_questions()` folds it into a `Question`, discarding `type` and passing `expected_answer` through as `expected_answer_notes`). **Five checks — two on the question it writes, two on the model answer it writes, one on the sources behind both.** (1) *Type recall* (deterministic): for each golden `(concept, type)` pair in `golden.py`, did the generator produce at least one question of that type — pooled across all 11 concepts, ≥ `TYPE_RECALL_THRESHOLD = 0.7`. (2) *Source citation and assembly* (deterministic, `CaseResult.grounding_violations`): every cited id names a passage that was actually sent, at least one is cited, and `grounding` is exactly those passages joined. The last clause is the standing guard against a refactor letting model-typed text back into that field; passage construction is imported from `question_generator.source_passages()` rather than re-derived, so the suite cannot drift from the generator. This replaced truncation + token-coverage checks that were only needed while the model retyped passages itself (see Architecture). (3) *Evidence basis* (LLM-judged, `claude-haiku-4-5`, ≥ `EVIDENCE_BASIS_THRESHOLD = 0.85`): is the question itself answerable from the given evidence alone, with no outside domain knowledge? Deliberately weak — a yes/no plus one sentence, not a score.
  - `golden.py` hand-curates one or two genuinely-appropriate-type reference questions per concept (not all 5 types forced) plus each concept's `summary`/prerequisite-`evidence` text, written as close paraphrases of the Case 3 source text (not required to be verbatim, same as graph_builder's own summaries).
  - `tests/question_geval/conftest.py` overrides the parent `stub_question_generator` fixture as a no-op and skips the whole directory if `LLM_API_KEY` is unset, same pattern as the other two suites.
  - **Checks 4 and 5 grade the answer side**, added after the `expected_answer` bug fix (see Architecture). Until they existed the suite only tested the question-writing half of `question_generator`'s output, while the model-answer half — the entire rubric `evaluator.py` grades against — went untested. (4) *Expected-answer gradeability* (`CaseResult.expected_answer_violations`), fully deterministic, no LLM call: catches shapes the evaluator structurally cannot grade regardless of content — under `MIN_EXPECTED_ANSWER_CHARS = 40`, deferring to context it never receives (`_ANSWER_POINTER_RE`, e.g. "as the passage states"), or a verbatim copy of the `grounding` quote, which is precisely the old bug. Exact-match only on that last one, since a close paraphrase of the evidence is legitimate (for `conceptual_correctness` the ideal answer largely *is* the evidence restated). (5) *Answer quality* (`support.judge_answer_quality()`, `claude-haiku-4-5`), asserted as an aggregate rate ≥ `ANSWER_QUALITY_THRESHOLD = 0.9`: does the `expected_answer` actually and completely answer its own question, consistent with the evidence, standing on its own for a grader that never sees that evidence? The judge prompt carries two explicit allowances so it doesn't penalize correct behavior — describing what any valid answer must demonstrate (right for the open-ended types) and closely restating the evidence (right for `conceptual_correctness`). **Neither has been exercised against the live API yet** — both were added in the same change as the field, so the 3/3 figure below predates them.
  - **Live-run status: 5/5 passing** (224s). Everything below is confirmed against the real API. Getting there took four runs and fixed four distinct defects: (1) `expected_answer_notes` was a source quote rather than a statement of what an answer needs — fixed by the `expected_answer` field; (2) the model corrupted passages it retyped into `grounding` — fixed structurally by having it cite `source_ids` instead (the `write_amplification` em-dash that broke every prior run now arrives verbatim); (3) model answers leaked "The evidence explicitly states…" — fixed by reframing rule 8 around the student's voice; (4) evidence-basis sat at 0.75 then 0.83 against a 0.85 bar, which turned out to be *two* problems: real rule-4 violations (questions asking "why" where the evidence gives an outcome but no mechanism — improved by dropping a speculative `prerequisite_link` hint and tightening rule 4 plus the `conceptual_distinction`/`applied_reasoning` type descriptions, at no cost to type recall) and a miscalibrated judge (see check 3 above — it held all five types to a restatement bar, which `open_ended_example` and `applied_reasoning` can never meet by design).
  - **A green run is not self-evidently healthy here, so the suite always prints its metrics** (`pytest_terminal_summary` in `tests/question_geval/conftest.py`, reading `score_case`'s cache so it costs nothing and stays quiet when the suite skips). A passing assertion prints nothing, so the 5/5 run above left its actual rates unknown — and for the LLM-judged checks an exact 1.00 would mean the judge had stopped discriminating, which is indistinguishable from a healthy pass without the number. The summary also names every question the judges rejected, so a green run still shows you what to eyeball.
  - **Recalibrating a judge to make a test pass is a real hazard, so the type-awareness change was probed directly** rather than trusted because the suite went green: five questions from the failing run were re-judged in isolation (~5 cheap calls, no full run). Two still came back not-grounded, so the constructive-type band is not a blanket pass. The probe also corrected the triage twice — `memtable`'s burst-of-writes question, filed as a genuine violation, is now grounded on the defensible reading that the evidence does state the mechanism (memtable flushes to an SSTable past its threshold) and the old judge was demanding a deeper answer than the question asked; while `write_amplification`, predicted to be rescued, still fails. Rerun that probe rather than the whole suite when touching judge prompts.
  - Grounding-fidelity history, three prompt fixes deep before the structural fix retired the problem: (1) the first run found `question_generator.py` truncating a second evidence source mid-clause on `conceptual_distinction` questions (which combine two sources) — fixed by adding rule 7 to `_SYSTEM_PROMPT` ("treat each passage as atomic... quote every passage in full, never truncate mid-clause"); (2) re-running surfaced that the original sentence-split-based grounding check was itself flaky against the model's (delimiter-varying) multi-quote joining style — replaced with a truncation+coverage check; (3) `write_amplification` still reproducibly failed after both, with a *different* manifestation each run despite `temperature=0` (dropping a middle clause; dropping a trailing sentence; substituting an em-dash with a stray artifact) — all centered on one sentence whose content overlaps between the target's own summary and the `lsm_tree` prerequisite's evidence. Rule 7 was strengthened again and held for two runs, then regressed the moment rules 8-9 were added. That recurrence is what motivated dropping model-retyped quotes entirely (see Architecture): the failure mode is now unrepresentable rather than merely unlikely.

- **`backend/tests/diagnoser_geval/`** — a regression suite for `diagnoser.py`, built on 9 hand-authored diagnosis cases over the same Case 3 graph the other two suites use (concept shape imported from `tests/question_geval/golden.py`, so the three cannot disagree about the case; `golden._validate()` runs at import and fails loudly if a fixture references an unknown concept or claims a hop distance the graph doesn't support). Shaped differently from the other suites because the diagnoser is an agentic loop rather than a single call, which breaks three of their assumptions:
  - **The output isn't the whole behavior.** That it investigated before concluding, that the certainty gate held, that it stayed in budget — none of it appears in `DiagnosisResult`. Hence `diagnoser._diagnose_with_trace()`, the internal seam (same pattern as `_extract_raw_graph()` / `_generate_raw_for_concept()`) returning a `DiagnosisTrace` of turns used, tool calls, rejected submissions, concepts inspected, and whether the final turn was forced. Worth having regardless of tests: without it a diagnosis that burned five turns and three rejections looks identical to a clean first-turn hit in production logs too.
  - **Ground truth is interpretive**, unlike graph_geval's concepts (objectively in the text) or question_geval's closed `type` vocabulary. So each case carries `acceptable_suspects` (a set — any is a pass), `preferred_suspect` (reported, never asserted), and `forbidden_suspects` (zero tolerance). The forbidden sets carry most of the discriminating power: several cases have the student demonstrate mastery of a neighbouring concept, so naming it contradicts the evidence rather than merely being suboptimal.
  - **Trajectories vary more than outputs** — `temperature=0` pins each call, but a different tool choice on turn 2 changes everything downstream — so metrics are aggregate rates, not per-case assertions.
  - Five checks in three tiers: (1) invariants, deterministic and zero-tolerance — no answer leak (the suspect's summary must not surface in the question, checked as an exact substring *and* an 8-word shared run via `_leaked_span`, since a paraphrase leaks just as well; this was called load-bearing in the original stub's docstring and had never been checked), suspect reachable from the answered concept via `depends_on`, question/id/notes well-formed, budget respected; (2) accuracy against `acceptable_suspects` plus zero `forbidden_suspects`, **reported split by hop depth** — the number that says whether the agentic design beats the old `depends_on[0]` stub; (3) two `claude-haiku-4-5` judges — does the targeted question actually probe its suspect, and is the reasoning evidence-backed rather than plausible-sounding (the certainty requirement made observable, since the code gate can only enforce that the model *claimed* high confidence).
  - `tests/diagnoser_geval/probe.py` is the iteration tool, and it is the thing to reach for before a full run. `probe case <name>` runs one case and prints its whole trajectory; `probe judges` re-checks both judges against fixed good and bad inputs. It has already earned itself twice — catching an ambiguous word in a judge prompt ("do not *reward* restating the concept" read as *penalize*), and a harness bug where `judge_reasoning_quality` compared the model's quotes against `suspect.evidence` when evidence *about* a concept actually lives on its dependents (`Concept.evidence` maps a concept's own prerequisites to their justifying quotes, which is what `get_prereqs` surfaces). Re-run `probe judges` after any judge-prompt edit: a judge that stops discriminating makes the suite green while measuring nothing, and at exactly 1.00 that is indistinguishable from a healthy pass.
  - Loop mechanics are **not** here — they're deterministic against a fake client, so they live in the free `tests/test_diagnoser_loop.py` (turn budget, forced final turn, certainty-gate rejection, per-reason rejection messages, error recovery, id incrementing). `tests/test_diagnoser_geval_wiring.py` is the free smoke test for this suite, same role as question_geval's: it drives `score_all()` with fakes so a name only referenced inside the billed path fails in 0.03s instead of mid-run.
  - `pytest_terminal_summary` prints every metric plus a per-case trajectory table on pass as well as failure, for the same reason question_geval does.
  - **As of the last full run: 6/6 passing** over 9 cases — accuracy 0.89, 0 forbidden, 0 invariant violations, 0 spurious outside-graph disclosures, question relevance 0.89, reasoning grounded 1.00, every hop depth scoring (0/1/2/3). Multi-hop drilling works: the 2-hop and 3-hop cases both land correctly, which is what says the agentic loop earns its cost over the old `depends_on[0]` stub.
  - **The most useful finding came from the trajectory, not the assertions.** The first run passed 5/5 while **5 of 8 cases hit the forced final turn** — spending the entire budget on `get_prereqs` and never converging, so they never reached `pull_question_from_storage` or `generate_question` at all. Two lines of `_SYSTEM_PROMPT` were pushing toward it ("the root gap is often deeper than one hop"; "spend them investigating"), reworded so stopping early is the goal rather than a compromise: **forced-final went 5/8 → 0/8**, mean turns 4.4 → 3.6, accuracy unchanged at 0.88. That also settles `_MAX_TURNS`: 5 turns was never the constraint, the prompt was. Note this is only visible because the suite prints trajectory stats on a green run — the assertions passed identically before and after.
  - The tradeoff is worth knowing: less investigation means **more self-diagnosis**. Both post-change degradations are that one effect — `hash_index` moved from `append_only_log` to `hash_index` (still acceptable, no longer preferred), and `wal_missing_btree_pages` names `write_ahead_log` rather than tracing to `b_tree` (a stable MISS across both runs, deliberately left as a miss: a diagnoser that answers "the concept itself" for non-leaf concepts has stopped doing its job). More probing buys deeper tracing and costs turns; that is the lever.
  - **The general-knowledge escape hatch is wired but empirically unexercised.** When no concept in the graph explains the deficiency the diagnoser may diagnose from background knowledge instead (system prompt rule 3), setting `gap_is_outside_graph` on `submit_diagnosis` and passing `allow_general_knowledge` to `generate_question` so the nested generator's evidence-only rule is relaxed for that call. The disclosure leads `DiagnosisResult.reasoning`, which is what the answer endpoint returns to the student — reusing the channel that already carries the low-confidence note, so nothing new is plumbed through the API or the frontend types. Only the false-positive direction is asserted (`spurious_disclosures`): the notice is user-visible, so a spurious one is noise that trains students to ignore a warning meant to be rare, while a missed one merely leaves prior behavior in place. On the run above **recall was 0.00** — the one case built for it (`hash_lookup_is_background_knowledge`) was diagnosed as `hash_index` directly instead. That is ambiguous between the prompt rule not landing and the fixture's premise being wrong (the chapter does say "in-memory hash map", so reading that error as a `hash_index` gap is defensible), and one case is too thin to tell. Treat the positive path as untested.
  - Thresholds are deliberately loose, not yet tightened to observed performance. Two runs both scored exactly 7/8 accuracy, so raising `ACCURACY_THRESHOLD` from 0.75 to 0.85 would leave zero headroom — with 8 cases each worth 12.5%, one trajectory flip turns the suite red. The real regression detector is the per-case table in the terminal summary; the threshold only catches a collapse.

## Docker gotchas

- `docker-compose.override.yml` (auto-merged) is dev mode: vite dev server (Dockerfile `dev` target), `uvicorn --reload`, bind mounts. It uses `ports: !override` to replace (not append to) the base port mapping, and a **distinct image tag** (`comprehension-agent-frontend-dev`) so dev/prod builds don't clobber each other — if the frontend serves nothing on :5173, a stale image from the other mode is the likely cause; rebuild with `--build`.
- Prod frontend: nginx serves `dist/` and proxies `/api` → `backend:8000` (`frontend/nginx.conf`). Dev: vite proxies `/api` using `BACKEND_URL` env var (`vite.config.ts`).
- Backend `env_file: .env` means compose fails without `.env` — copy from `.env.example`.
- `postgres`'s host port is `5433`, not the standard `5432` — chosen to avoid colliding with a locally-installed Postgres. Only matters for connecting from the host (native `uvicorn`, `psql`, a GUI client); inside the compose network the `backend` service reaches it as `postgres:5432` (the container-internal port), via a `DATABASE_URL` override in `docker-compose.yml` that takes precedence over whatever `.env` provides through `env_file`. Because `postgres` is a compose service now, plain `docker compose up` (no args) starts it even though nothing depends on it yet — harmless, but a behavior change from before this existed.
